# Technical design: Note creation templates

Status: Phase 1 (data model, resolver, Settings UI), Phase 2 (Meeting notes) and Phase 3 (Todo notes + cleanup) implemented and committed 2026-09-18; none of the three phases has been smoke-tested on a real Supernote device yet (§9's standing per-phase requirement — this session has no access to the physical device, only to the Windows dev machine, so every on-device check listed in this doc is still owed whenever Tilman next has the device in hand). Phase 3 is, per Tilman's own framing when requesting it, **the last piece of this feature planned for now** — Phase 4 (standalone notes) and Phase 5 (the deferred list, §7) are documented but not scheduled. Requirements clarified in chat (4 rounds for Phase 1, a further round for Phase 3) and a click-through UI draft (3 rounds) before implementation started, per this project's standing workflow. UI draft: "Note Template Manager" artifact (not linked here — artifact URLs aren't stable project memory; it's in Tilman's artifact gallery).

## 1. What this replaces and what it adds

Today the plugin has three separate note-creation paths and one piece of real "template" logic, none of it shared:

- `storage/noteLinks.ts`'s `createLinkedNote` — a `.note` file tied to a Task or Meeting, in a fixed `Todos/`/`Meetings/` subfolder. Gets a background via `getNoteTemplate(settings)` (one global filename). Gets **no auto-inserted content at all for Todos**; for Meetings, content comes from a second call (`refreshMeetingNoteBlock`, below).
- `storage/standaloneNotes.ts`'s `createStandaloneNote` — an untracked `.note` file wherever the Files pane is browsing. Same global background. No auto-inserted content.
- `domain/meetingNoteBlock.ts` + `storage/meetingNoteContent.ts` — the one place with real content logic: `buildMeetingNoteText` hardcodes "title, date, Relevant Todos:" into one string, `relevantTodosForMeeting` matches open todos to a meeting by shared tag, `populateMeetingNoteBlock` writes it as one userData-tagged textbox (+ an optional "Link:" element) at one global anchor position (`settings.meetingNoteBlockTopX/Y/MaxWidth`).

This feature generalizes that last piece into something every creation path can use, and wires all three paths through it: a small, user-editable catalog of **note creation definitions** — context (Project/Area/Todo/Meeting) + optional tag + background + an ordered set of content **pieces**, each with its own position and font size — resolved by a single function and rendered by a generalized version of the element-writing code that already exists for meetings.

No new note *kinds* and no new creation surfaces. Every place this plugin already creates a note keeps creating it exactly where it does today; the only change is that each of those call sites asks the new resolver what to insert instead of hardcoding it (or, for Todos, inserting nothing).

## 2. Data model (`domain/noteTemplate.ts`, new — zero RN imports, per design-overview.md §3)

```ts
export type NoteContext = 'project' | 'area' | 'todo' | 'meeting';
export type PieceType = 'title' | 'date' | 'time' | 'text' | 'related';

export interface NotePiece {
  type: PieceType;
  /** Only meaningful for type === 'text' — the user's own text, verbatim. When `textId` is set this is a denormalized copy of that NoteTextItem's text, kept in sync on save (§6.1), so rendering never looks anything up. */
  text?: string;
  /** Only for type === 'text' — which of the definition's `texts` this piece places (§6.1). Absent on pieces saved before rule-owned texts existed. */
  textId?: string;
  x: number;
  y: number;
  fontSize: number;
  /** Last nudge-step (5 or 25) used on this piece — UI memory only, not read by rendering. */
  step: number;
}

/** 2026-09-20 (§6.1): a reusable static text that belongs to exactly ONE rule. */
export interface NoteTextItem {
  id: string;   // "t1", "t2", … — counter over the rule's own list, only meaningful inside one rule
  name: string; // row label on the Add-piece page
  text: string;
}

export interface NoteCreationDefinition {
  id: string;
  name: string;
  context: NoteContext;
  /** Empty = never matched by tag; only reachable via isDefault. */
  tags: string[];
  isDefault: boolean;
  enabled: boolean;
  /** '' = blank (style_white); else a MYSTYLE_FOLDER filename, same convention getNoteTemplate already uses. */
  template: string;
  pieces: NotePiece[];
  /** This rule's own static texts (§6.1). Optional: rules saved before this existed need no migration (absent === none). */
  texts?: NoteTextItem[];
}

export const PIECE_CONTEXTS: Record<PieceType, NoteContext[]> = {
  title:   ['project', 'area', 'todo', 'meeting'],
  date:    ['meeting'],
  time:    ['meeting'],
  text:    ['project', 'area', 'todo', 'meeting'],
  related: ['todo', 'meeting'],
};
```

`related` carries **no** per-piece tag override — it always matches by whichever tags the note being created actually has, the same way `relevantTodosForMeeting` already reads `meeting.tags` directly rather than a configured value. One fewer field to design a UI for, and it can never drift out of sync with the note's own tags.

**Implementation note (2026-09-18): tag matching is case-insensitive; the config's own tags are normalized to lowercase.** Tilman: "tags should be normalized to small in the config and be applied case insensitive." Two changes, belt-and-suspenders rather than relying on just one: (1) `screens/Settings.tsx`'s `handleSaveDefinitionDraft` lowercases the parsed tag list before it's written into `NoteCreationDefinition.tags`, so the config itself — what a definition actually stores — is always lowercase regardless of how the user typed it (`#Coaching` and `#coaching` both save as `coaching`). (2) `resolveNoteTemplate` additionally lowercases both sides of its own comparison rather than trusting (1) alone — the note's own tags (a Meeting's, say) come from user-entered text elsewhere in the app that was never asked to normalize its casing, and this way the match is correct regardless of what either side actually stored, including any already-saved config data from before this fix.

**Decided** (previously open questions, resolved with Tilman 2026-09-18):

- **Piece width is not a stored field.** A piece always extends from its own `x` to the page's right edge — no per-piece width to configure or drag, matching the UI draft's "just the upper-left corner." `domain/noteTemplate.ts` adds:
  ```ts
  /** Supernote A5X page width in device px — design-device-rendering.md. */
  export const NOTE_PAGE_WIDTH_PX = 1404;
  export function pieceWidthPx(x: number): number {
    return Math.max(0, NOTE_PAGE_WIDTH_PX - x);
  }
  ```
  This is the one place both the Settings-UI preview and (from Phase 2 on) the real element writer get a piece's width from — no second copy of "page width" anywhere.
- **Definition/piece IDs are a simple incrementing counter**, not a UUID — `GtdParaSettings` gains `nextNoteDefinitionId: number` (default `1`) alongside `noteCreationDefinitions`, incremented each time a new definition is created, mirroring the UI draft's own `nextId`. Tilman flagged export/import of definitions as a plausible future idea this doesn't need to accommodate now — noted under Outstanding scope (§7 Phase 5), not designed here.
- **New-piece seed position is `x: 100, y: 100`** — not a mirror of today's `meetingNoteBlockTopX/Y` (60/60). This is a deliberate, explicit choice (not a migration oversight — see §7 Phase 2's note on this). `domain/noteTemplate.ts` adds:
  ```ts
  export const DEFAULT_PIECE_X = 100;
  export const DEFAULT_PIECE_Y = 100;
  ```
  The first piece added to an empty definition seeds here; every piece after that stacks below the lowest existing piece (mirrors the UI draft's `addPiece` helper) rather than re-seeding to 100/100.

  A new piece's starting `fontSize`/nudge `step` are the same `domain/noteTemplate.ts` constants, `DEFAULT_PIECE_FONT_SIZE`/`DEFAULT_PIECE_STEP` — both retuned 2026-09-18 (Tilman: "set the default size for text to 36, this is the default smallest size on supernote notes and looks much better. Set default moving speed to 25 instead of 5"), from 17px (a mirror of `ui/theme.ts`'s `FONT.medium`, tuned for this app's own small Settings UI, not for a note page) to 36px, and from 5 to 25. Both stay adjustable per-piece afterward exactly as before — `ui/NudgePad.tsx`'s two step buttons (5/25) and font ± stepper are unchanged — this only changes what a *newly added* piece starts at.

### Resolution

```ts
export function resolveNoteTemplate(
  context: NoteContext,
  tags: string[],
  definitions: NoteCreationDefinition[],
): NoteCreationDefinition | null {
  const inContext = definitions.filter(d => d.enabled && d.context === context);
  for (const d of inContext) {
    if (d.tags.length > 0 && d.tags.some(t => tags.includes(t))) return d;
  }
  return inContext.find(d => d.isDefault) ?? null;
}
```

First enabled, tagged definition (in list order — list order doubles as priority, same "first match wins" rule `domain/abbrev.ts`'s quick-file already established) whose tag overlaps the note's own tags; otherwise the context's Default; otherwise `null`. Every caller treats `null` as "blank template, no pieces" — today's behavior — so a fresh install with zero definitions configured is unchanged.

## 3. Where definitions live

Plugin config, not PARA content — design-overview.md §3 is explicit that `AsyncStorage` is for configuration only, never Task/Meeting *content*, and a note-creation rule is squarely configuration. `GtdParaSettings` (`domain/settings.ts`) gains:

```ts
noteCreationDefinitions: NoteCreationDefinition[];
nextNoteDefinitionId: number;
```

defaulting to `[]` and `1` respectively in `DEFAULT_SETTINGS`. `storage/settingsStorage.ts`'s `loadSettings`/`saveSettings` need no change — they already spread over `DEFAULT_SETTINGS`, so an old saved blob missing these fields just gets the defaults for free.

### Retiring the settings this replaces

`settings.meetingNoteTemplate` and `meetingNoteBlockTopX/Y/MaxWidth` become dead weight once every note-creation path resolves a definition instead of reading these directly. Decision: retire them in Phase 2, not leave them as a second, unused config surface next to the new one — this is exactly the kind of duplication worth cleaning up while the surrounding code is already being touched. `getNoteTemplate(settings)` itself is **not** deleted: it keeps its current signature and becomes the literal bottom of the fallback chain (`resolveNoteTemplate` returning `null` → still call `getNoteTemplate`/`BLANK_TEMPLATE_NAME` for the background) — the single-lookup-point seam that function's own doc comment was already built for.

**Implementation note (2026-09-18): only partially retired, on purpose.** `meetingNoteBlockTopX/Y/MaxWidth` are fully gone from `GtdParaSettings` — nothing read them except the old fixed-block positioning, which Phase 2 fully replaces (the fallback path uses small hardcoded constants instead, see storage/meetingNoteContent.ts). `meetingNoteTemplate` was **not** retired: it turned out to still be the only thing that picks a note's *background*, at *creation* time (`storage/noteLinks.ts`'s `createLinkedNote`/`storage/standaloneNotes.ts`'s `createStandaloneNote`, both called before any content step runs) — genuinely separate from the *content* pieces this phase wires through the resolver. A `NoteCreationDefinition`'s own `template` field existed and was editable but wasn't consumed anywhere at creation time yet — flagged as a real gap, deferred to whenever Phase 3 touched these same call sites anyway.

**Bugfix (2026-09-18, same day, closed early): background gap fixed for `createLinkedNote`.** Tilman, testing Phase 2 + the real-image work above: "right now the template selected in the note creation definition seems not to be used when creating the note, the content is inserted correctly as defined, but not the background." Root cause confirmed exactly as this note predicted: `createLinkedNote` always called `getNoteTemplate(settings)` (the global setting) for a note's background, completely independent of `refreshMeetingNoteBlock`'s `resolveNoteTemplate` call for content — so a definition's `template` field was stored and shown in Settings but never read at creation time. Fixed via a new `storage/noteLinks.ts` export, `resolveNoteBackgroundTemplate(settings, context, tags)`: calls the same `resolveNoteTemplate(context, tags, settings.noteCreationDefinitions)` content already uses, and returns the resolved definition's `template` (or `getNoteTemplate(settings)` when nothing matches — same fallback content already has via `populateMeetingNoteBlockFallback`). `createLinkedNote` gained one new parameter, `tags: string[]` (not `context` — derived internally from the existing `subfolder` param, since the two always move in lockstep at every call site); `context` is `'meeting'`/`'todo'` depending on `subfolder`. All nine `createLinkedNote` call sites (WeekView/InboxScreen ×2/ReviewScreen ×2/DailyView ×2/ProjectDataPanel ×2) updated to pass the Task's/Meeting's own `.tags` — each call site already had that object in hand, so this was a mechanical one-line addition per site, not new data-plumbing. This incidentally also makes Todo-context definitions' backgrounds take effect at creation time, ahead of Phase 3's content wiring for Todos — harmless (a Todo note just gets the right background with no auto-inserted content yet, same as before Phase 3). `storage/standaloneNotes.ts`'s `createStandaloneNote` (Project/Area context) is intentionally untouched — still Phase 4 scope, still reads `getNoteTemplate(settings)` directly. `tsc`-clean (only the pre-existing unrelated `ClipboardTextInput.tsx` error), committed and re-staged/md5-verified byte-identical across all nine files on the first attempt. **On-device confirmation still owed** — nobody has created a note against a tagged definition on the real hardware since this fix landed.

## 4. Content rendering — generalizing the meeting-note code

Rename `storage/meetingNoteContent.ts` → `storage/noteTemplateContent.ts` (its scope is no longer meeting-only; keeping the old name once it renders Todo/Project/Area pieces too would be actively misleading, the same care this codebase already takes elsewhere — e.g. `getNoteTemplate`'s own doc comment flagging its own past meeting-only name as a thing to fix).

**Implementation note (2026-09-18): file renames deferred, exports renamed in place.** This session's device bridge can stage/commit files but has no delete capability, so a true rename would leave an orphaned, un-deletable duplicate on disk rather than a clean move. `domain/meetingNoteBlock.ts` and `storage/meetingNoteContent.ts` keep their current filenames for now (both files' own doc comments flag this, with the exact manual rename steps) — every export inside them IS renamed/generalized as planned (`estimatePieceTextHeight`, `noteLinkLineHeight`, `NOTE_LINK_USERDATA`, `notePieceUserData`, `isNoteTemplateManagedElement`). No call site needed touching as a result — `refreshMeetingNoteBlock`'s import path and signature are both unchanged, so DailyView.tsx/InboxScreen.tsx/ReviewScreen.tsx/ProjectDataPanel.tsx needed zero edits for this phase.

**New pure function**, `domain/noteTemplate.ts`, `renderPieceText(piece, ctx)`:

| piece.type | source |
|---|---|
| `title` | the note's own title/text |
| `date` | formatted date — meeting only |
| `time` | formatted time, only when set — meeting only |
| `text` | `piece.text`, verbatim |
| `related` | a heading + bullet list from a generalized matcher (below) |

**Generalizing `relevantTodosForMeeting`**: today's function (`storage/meetingNoteAggregate.ts`) is already "tag-match only, independent of flow-state" and already takes `items`/`inbox` generically — the only meeting-specific part is its name and its `Pick<Meeting, 'tags'>` parameter. Widen it to `relatedItemsFor(items, inbox, tags: string[])`, taking a plain tag list instead of a `Meeting`. Every existing call site (meeting notes) passes `meeting.tags` exactly as before — no behavior change, just a rename plus a narrower parameter. A future Todo caller passes `task.tags` the same way. **This is a rename+widen, not a new function** — resist writing a second near-duplicate matcher for Todos.

**Implementation note (2026-09-18, Phase 3): `relatedItemsFor` widened once more, with a 4th optional param.** The "future Todo caller" above landed — and immediately hit a case Meetings never had: a Todo calling this with its own `task.tags` would match *itself* (a task sharing a tag with itself is still a tag match). `relatedItemsFor(items, inbox, tags, excludeNotePath?)` — a task whose own `notePath` equals `excludeNotePath` is skipped. Tasks have no `id` field to filter by more precisely, but every real caller only ever passes this once `task.notePath` is already set (`refreshTodoNoteBlock`'s own `if (!task.notePath) return` guard), so excluding by `notePath` is safe in practice.

**Height estimation**: `estimateMeetingNoteBlockHeight`/`meetingNoteLinkLineHeight` (`domain/meetingNoteBlock.ts`) are already piece-agnostic — they take `text`/`fontSizePx`, nothing meeting-specific. Reused as-is, just called once per piece instead of once for a whole hardcoded block. Rename the file `domain/meetingNoteBlock.ts` → `domain/notePieceBlock.ts` alongside the storage-layer rename, same reasoning.

**Element writer**: generalize `populateMeetingNoteBlock` → `populateNoteFromDefinition(notePath, definition, pieceContent: string[], settings)`:

- Same shape as today: read every element on page 0, delete any carrying this feature's userData marker, insert the fresh set in one `insertElements` call (so a partial failure can't leave a half-written note).
- userData marker becomes per-piece-index (`gtdpara:note-piece:<index>:v1`) instead of one fixed marker, since piece count and order are now data-driven rather than fixed at "one block + optional link."
- Each piece is positioned at its own stored `x`/`y`/`fontSize` rather than one global anchor.

**Implementation note (2026-09-18): `settings` dropped from `populateNoteFromDefinition`'s signature.** Once `meetingNoteBlockTopX/Y/MaxWidth` were retired (§3) and positioning became fully piece-driven, nothing in `GtdParaSettings` was actually read by this function anymore — background selection happens earlier, at creation time (§3's implementation note), not here. Kept the signature honest rather than carrying a dead parameter the design called for; `populateMeetingNoteBlock` was renamed to `populateMeetingNoteBlockFallback` (not deleted) — it's still reachable, as the fallback for a Meeting with no matching/enabled definition, and both it and `populateNoteFromDefinition` clean up the *union* of every marker this feature has ever written (old fixed-block marker, link marker, per-piece markers) via a shared `isNoteTemplateManagedElement` check, so switching a Meeting between the two shapes across regenerations never leaves a stale duplicate behind. The old "Link:" element logic was factored into one shared `buildLinkElement` helper both population functions call, rather than duplicated.

**Explicitly out of scope for this pass**: the meeting-note block's existing "Link:" element (shown when `meeting.linkedFile`/`task.linkedFile` is set) is **not** folded into the piece system yet. It keeps today's behavior exactly — auto-appended below the last piece, same positioning logic as today. The UI draft never modeled a "linked file" piece type, so this isn't a decided requirement; noted under Outstanding scope (§7 Phase 5 #2) rather than invented here. **Superseded 2026-09-25** by `technical-design-linked-file-piece.md`: the link is now a placeable piece, and the fallback block is gone.

## 5. Wiring every creation path through the resolver

- **Meeting notes** (`storage/meetingNoteContent.ts` → `noteTemplateContent.ts`): `refreshMeetingNoteBlock` calls `resolveNoteTemplate('meeting', meeting.tags, settings.noteCreationDefinitions)`, renders each piece via `renderPieceText`, calls `populateNoteFromDefinition`. If resolution returns `null`, behavior is unchanged from before this feature existed (today's fixed title+date+related-todos shape) — see the migration note in Phase 2.
- **Todo notes — DONE, Phase 3 (2026-09-18).** `refreshTodoNoteBlock(task, itemPath, settings, inbox?, options?)`, same shape as `refreshMeetingNoteBlock` (including the same `inbox` param for the two Inbox-scoped screens, and the same `options.isInitialPopulation` bypass — see the freeze-rule implementation note below) — wired into all 8 real call sites: `ProjectDataPanel.tsx`'s TodosSection (`handleCreateNote`/`handleOpenNote`), `DailyView.tsx`, `ReviewScreen.tsx`'s Inbox tasks, `InboxScreen.tsx`. No fallback-block path (unlike Meetings) — Todos never had a pre-existing fixed shape to preserve, so `resolveNoteTemplate('todo', ...)` returning `null` just means nothing gets written, same "blank note" behavior as before this feature. Title piece uses a new `domain/markdown.ts` helper, `stripAllTags(task.text)`, not `task.text` verbatim — a task's text routinely carries trailing `#next`/context tags that don't belong in a note's title (unlike a Meeting's title). Related-items piece reuses `relatedItemsFor`, widened with an `excludeNotePath` param (§4) so a Todo note never lists itself.
- **Standalone notes** (`storage/standaloneNotes.ts`): `createStandaloneNote` already receives `tags: string[]` — extracted from the title before stripping, for `insertKeyWord` — and a `folderPath` but no `context`. Add a `context: 'project' | 'area'` parameter (the caller, `ProjectDataPanel.tsx`'s note-mini-tab handler, already knows its own `kind`), then call `resolveNoteTemplate(context, tags, settings.noteCreationDefinitions)` and `populateNoteFromDefinition` right after `createNote` succeeds — **reusing the same already-extracted `tags` array** that already drives `insertKeyWord`. One extraction, two uses; don't extract tags a second time for template resolution.
- **Project/Area "main note"**: not built. The context/resolver design already supports it (nothing blocks adding a dedicated entry point later that just calls the same `createStandaloneNote`+resolver path against a fixed name), but no new entry point ships in this feature — confirmed out of scope for now (§7's Phase 4 covers only the existing standalone-note tab).

### 6.1 "Add piece" as a general piece editor — rule-owned static texts, once-only placement (2026-09-20)

**Requirements** (Tilman, chat, with an HTML prototype `add-piece-prototype-v2.html`): edit static texts from the tag-rule screen; they appear next to the predefined pieces on the Add-piece page; tapping a row never adds anything — it selects it; the right side then edits (a text) or explains (a predefined piece: description + example) and stays empty until something is selected. Other pieces may get options later (e.g. a date format), so the page is designed as a general editor, not a text composer.

**Decisions**
- Texts belong to **one rule** (no global library, no cross-rule sharing) and live in `NoteCreationDefinition.texts`. Editing a text updates its **placed piece in place** (position/font/step untouched) — the piece points at the text by `textId`.
- **Every piece is placed at most once per rule** (a predefined type by type; a text by `textId`). A placed row's "+ Add" becomes **"Remove"**; removing a text piece only takes it off the page — the text stays in the list. Deleting a text is a separate action in the right panel and, when the text is placed, needs a confirming second tap because it also removes the placed piece. Options (none built yet) would belong to that one placement.
- **"+ Add" / "Remove" keep the page open** so several pieces can be placed per visit; "‹ Back to rule" returns to the edit form. A newly added piece is selected, so the NudgePad on the edit form already points at it.
- Everything is edited on the Add-piece page only — **no separate management screen** (an earlier sketch had one; dropped once texts became per-rule). Texts are part of the rule draft, so they save/discard with the rule's own Create/Save/Cancel (no separate persistence path).
- Name = required row label (defaults to "Untitled"); a text is available in **all four contexts**.

**Data / domain** (`domain/noteTemplate.ts`, pure): `NoteTextItem`, `NotePiece.textId`, `NoteCreationDefinition.texts`; helpers `definitionTexts`, `findPlacedPieceIndex`, `isPiecePlaced`, `removePlacedPiece`, `nextTextItemId`, `addTextItem`, `updateTextItem` (also syncs the placed piece's `text`), `removeTextItem` (also removes its placed piece), `migrateLegacyTextPieces`; `addPieceToDefinition` gained an optional `textId`. **Rendering is unchanged**: `renderPieceText` still reads `piece.text`, which `updateTextItem` keeps in sync — so nothing in `storage/` changed.

**Existing rules.** Text pieces saved before this (inline `text`, no `textId`) are migrated **when their rule is opened for editing** (`handleEditDefinition` → `migrateLegacyTextPieces`): each becomes a named text of that rule (first line, ≤24 chars, "Text" if empty), keeping its text, position and font; it only reaches disk if the rule is then saved — until then rendering is unaffected either way. Duplicates of Title/Date/Time/Related items created before the once-only rule are left alone: the row shows as placed and "Remove" peels them off one at a time (`removePlacedPiece` removes the first match).

**UI** (`screens/Settings.tsx`, `templatesView === 'edit-piece'`): same stretched two-column shape as the Choose-background page. Left card: a self-measuring `PagedSection<AddPieceRow>` (predefined pieces for the rule's context, then the rule's texts; rows 44px + 6px margin, ✓ on placed ones, a small outlined "+ Add" / filled "Remove" button on the right, a one-line text preview under a text's name), and a pinned "+ New text" under the list (not a row in it, so it can never land on a later page). Right card: nothing until selected; a predefined piece shows its status, description and an **example built from the real render logic** (the date example even calls `formatFullDate`); a text shows Name + Text fields (`ClipboardTextInput`, each wrapped in `clipboardFieldRow` to avoid the known `flex: 1` growth) with Create/Save and Delete. A one-line notice under the columns reports the last add/remove/save. `staticTextDraft` and `handleAddPiece` were removed.

**Not built (deliberately):** per-piece options such as a Date/Time format (the prototype's "future option" was an illustration only); re-adding a removed piece re-seeds its position below the last piece rather than remembering the old one (accepted).

**Verified:** 42-check standalone-Node script over the new domain helpers (placement, in-place edit keeps position/font, remove keeps the text, delete removes the placement, duplicates peel off one at a time, legacy migration incl. idempotence/id continuation); strict `tsc --noEmit` clean over `screens/Settings.tsx`, `storage/meetingNoteContent.ts`, `ui/NoteTemplatePreview.tsx` and their import graph. **On-device confirmation still owed**: the paged list self-measuring in the stretched column, "+ Add"/"Remove" flipping and the page staying open, Save updating a placed text without moving it, the confirm-delete flow, and a legacy rule's texts appearing as named texts.

## 11. Textbox sizing — reusing the sibling project's calibration

Tilman pointed at `NoteDraft/textboxHelper/src/shared/supernoteTextboxLayout.ts` (a sibling plugin project) before implementation started: "It contains logic for creating textBoxes with the right sizing on supernote. This avoids strange effects, when the box does not fit the content."

**What that file does**: prefers a real Android text measurement via a custom native module (`NativeModules.TextboxMetrics`), and falls back to a heuristic line-count estimate when that module isn't available. Both paths subtract a calibrated `widthAdjustment` (30px, "learned from device testing") from the textbox's nominal width before estimating/measuring, specifically to stop content from overflowing the box.

**What's reusable here, and what isn't**:

- The native `TextboxMetrics` module **cannot be reused as-is** — gtdpara has no such native module (only `GtdParaFileModule.kt` exists on the Android side), and porting a native text-measurement bridge is a separate, much larger piece of work than this feature. Not in scope unless separately requested.
- The fallback heuristic's own tuning constants (`LINE_HEIGHT_FACTOR`, `BOX_HORIZONTAL_PADDING_FACTOR`, `BOX_VERTICAL_PADDING_FACTOR`) are **not** being ported either. gtdpara already has its own, already-reused, already-once-device-calibrated line estimator (`ui/textLineEstimator.ts`'s `activeLineEstimator.estimateLines`, which `estimateMeetingNoteBlockHeight` already builds on and §8 already commits to reusing unchanged). That module's own doc comment is explicit that it's "deliberately pluggable at the whole-algorithm level" specifically so a better implementation can later replace it at its one swap point — introducing a second, differently-tuned height formula alongside it here would fragment estimation into two parallel algorithms, the exact thing that design already exists to prevent.
- The **`widthAdjustment` idea itself** — trimming a small calibrated inset off the box's nominal width before estimating, because real glyphs render slightly wider than a naive width assumption — is the genuinely reusable insight, and gtdpara has already independently hit and fixed the same class of problem once: `ui/textLineEstimator.ts`'s `AVAILABLE_WIDTH_SAFETY_MARGIN` (added 2026-09-15 after a real on-device smoke test found predicted-one-line titles actually wrapping to two). That's this codebase's existing version of the same correction, tuned as a ratio rather than a fixed pixel inset.

**Plan** (a Phase 2 concern — Phase 1 only needs `pieceWidthPx` for the Settings-UI preview's rough layout, not exact on-device text fit): when Phase 2 generalizes `estimateMeetingNoteBlockHeight` into the per-piece height estimator, additionally trim a small fixed inset off the width computed by `pieceWidthPx(x)` before it reaches `activeLineEstimator.estimateLines` — mirroring the sibling project's `widthAdjustment`, seeded at the same 30px starting value since it's a real device-learned number, but treated as its own named constant (e.g. `TEXTBOX_WIDTH_INSET_PX`) to retune from an on-device screenshot if needed — same "hand-tuned starting point, recalibrate from real testing" convention `ui/textLineEstimator.ts` and `ui/pagination.ts`'s `PAGE_SIZE` constants already follow. No new estimation module, no native-module port — one existing estimator, one existing single swap point, one small additional constant.
