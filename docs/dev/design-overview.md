# gtdpara — Architecture & Design Reference

> **About this document.** The architecture of gtdpara as it is built and intended now: the
> vision, how the app is put together (screens, data model and file format, cache, notes,
> integrations, settings), the binding architecture rules (§3) and the reasons behind the main
> design choices. It is written in present tense and describes the current state only - no
> history, no "previously", no open work. Open questions, ideas and known debt go to the internal
> backlog; how a feature came about is in its technical design (`technical-design-*.md`, kept as
> history) and in git. Update the affected section in the same change that alters the
> architecture or a rule (`DEVELOPMENT-POLICY.md` §6). gtdpara is a filesystem-first PARA + GTD
> layer for the Supernote, built independently from SNFolio (informed by it, not forked from it).

---

## 1. Vision

A minimal plugin that organizes work using PARA (Projects, Areas, Resources, Archive) for filing and GTD conventions for doing — where the *files themselves*, not an internal plugin database, are the source of truth. Every piece of data the plugin manages is readable and (mostly) editable in a plain text editor or Obsidian, with or without the plugin installed. No calendar/CalDAV sync — that's the one subsystem that can't be filesystem-native, so it stays out of scope entirely, not just deferred.

## 2. Current implementation

### 2.1 Screens and navigation

**Superseded by a tab-based refactor since this section was first written** — the "Six screens/state machine" model below no longer matches `App.tsx`. Eight screens now live in `src/screens/`, but navigation is `src/ui/TabBar.tsx`'s seven persistent tabs plus one full-screen overlay, not a `Screen` union/back-stack. Three independent pieces of state in `App.tsx` drive it: `mode: 'loading' | 'capture' | 'tabs'` (whether the tab shell or the Lasso-capture overlay is on screen at all, or neither yet), `activeTab: AppTab` (`'projects' | 'areas' | 'daily' | 'inbox' | 'current' | 'review' | 'settings'` — which tab is showing), and `currentItem: CurrentItem | null` (what the "Current" tab shows). Switching tabs and back leaves `currentItem` untouched — there's no navigation history to manage, and no per-screen "‹ Back" left anywhere. A fourth piece, `settings: GtdParaSettings | null`, was added alongside these specifically to feed the Review tab's star badge (below) without every screen needing its own settings load.

`TabBar` renders the seven tabs — **Projects, Areas, Daily, Inbox, Current, Review, Settings** — plus a single "✕ Close plugin" action (`PluginManager.closePluginView()`) that's always visible regardless of which tab is active. This replaced an earlier per-screen header convention (Home/DailyView/ItemDetail/Settings each used to render their own "‹ Back" + "✕"): a new screen just needs a tab, not its own header/close affordance. Screens have no heading and no refresh button of their own, and the tab bar has none either: **Settings → Advanced → "Reload all files"** rebuilds the cache (`rebuildCache`) and drops every kept tab (`ui/keepAliveStore.ts`'s `dropKeptTabs`, App.tsx clears its visited set), so each tab loads again from the files on its next visit.

- **Projects / Areas** — `ItemsList`, one component for both (`kind: 'project' | 'area'` prop), rendered from whatever's in the cache (§2.3), refreshed via the shared icon above (§2.15) rather than its own button. Replaced the old two-column Home screen once Projects and Areas became separate tabs. Grouped by status (§2.12): Active (focus-first, §2.10), then On Hold, then — Projects only — "Done — awaiting review"; a group with nothing in it is simply omitted. Resources and Archive are hidden *and not scanned at all* — a deliberate scope-narrowing decision, not a bug.
- **Daily** — `DailyView`. A two-column row (Calendar left, Open tasks right, each independently scrollable), then a two-column Focus row (Projects | Areas, §2.10) at the bottom. Inbox no longer has its own section here (§2.16) — its qualifying tasks/meetings flow into these same two columns instead, labeled "Inbox" the same way any Project/Area is. Meetings/Open-tasks rows carry full inline edit/cancel/note parity, plus a quick-add for a Task or Meeting with a Project/Area/Inbox destination picker, positioned above the content it adds to (§2.15). See §2.11 for the full writeup.
- **Inbox** — `InboxScreen` (§2.16, 2026-09-03) — the fallback destination for tasks/meetings with no Project/Area. Same two-pane shape as Current below but without Status/Focus/Archive/Files (nothing there to show): Meetings take the left pane, Tasks the right, both unfiltered (no today/tomorrow-style window) and both with full row parity including the File action (move an item into a Project/Area).
- **Current** — `ItemDetail`, showing whichever Project/Area `currentItem` points at (an empty-state hint if nothing's been opened yet this session — opened from Projects/Areas/Daily, from a Lasso-capture save, or by `reorient()` below). Left pane: a live, un-cached drill-down file browser (tap a folder to go in, "‹ Up" to back out, tap a file to open it via the native open-file call) — this is raw folder listing, a different kind of data than tasks/meetings, so it's intentionally exempt from the caching rules in §2.3 and always re-scans the current folder level on open — followed by `ItemStatusPanel` (§2.16), the item's own Status picker and Archive action, below the file list. Right pane: `ProjectDataPanel`, always scoped to the *item's own root* regardless of how deep the left pane is browsed, since Tasks/Meetings live in the root's own data file, not wherever the file browser happens to be — the item's own Focus checkboxes (§2.10), Todos, and Meetings, full create/edit/soft-delete for the latter two; see §2.2 for the data model and §2.3 for how it reads/writes through the cache. Archiving (`onArchived`, now sourced from `ItemStatusPanel` and threaded up through `ItemDetail` to `App.tsx`) clears `currentItem` and switches back to the Projects/Areas tab the item came from, since `currentItem.path` stops resolving to anything real once the folder has moved. "Reload all files" (§2.1) remounts this screen, which loads the item again; the file browser re-scans its folder on every (re)mount.
- **Review** — `ReviewScreen`, a 9-step Weekly Review wizard. See §2.13 for the full writeup, and §2.15 for its own header removal/quick-add repositioning.
- **Settings** — the base storage root plus a folder name for each of Projects/Areas/Resources/Archive, with a live path preview per field, plus the four daily/weekly focus slot counts (§2.10). Saving clears the cache (§2.3) so a changed root can't leave stale data on screen. No heading of its own. Its Advanced tab holds "Reload all files" (§2.1).
- **CaptureScreen** — the Lasso-capture flow (§2.9), reached via `mode: 'capture'` rather than being one of the seven tabs — it overlays the tab shell entirely rather than sharing `TabBar`. Recognizes the active lasso selection into editable text, then Todo/Meeting + destination + optional source-link, then saves through the same write paths as ProjectDataPanel/Inbox.

**Opening and re-opening the plugin.** `App.tsx`'s mount effect does two things every time it runs: it looks up the note that was open when the plugin launched (`PluginCommAPI.getCurrentFilePath`) and jumps straight into that note's enclosing Project/Area if it has one (`findEnclosingItem`, `domain/settings.ts` — walks up through any nesting, e.g. a note inside a Project's own `Meetings/` subfolder still resolves to that Project), setting `currentItem` and switching to the "Current" tab; a miss switches to the **Daily** tab instead (the closest still-useful landing spot now that there's no Home tab) without touching whatever `currentItem` already held. It also kicks off a background cache rebuild (§2.3). Critically, this doesn't only run once: it's also wired to the plugin's own sidebar button via `PluginManager.registerButtonListener`, filtered to that button's id (`domain/buttonIds.ts`'s `SIDEBAR_BUTTON_ID`). The JS instance stays alive while the plugin is merely hidden (the user switched to a different note without tapping "✕"), so without this, re-tapping the sidebar button from a different note would leave the plugin stuck showing whatever it had open before. Registering for the button event, not just the mount, is what makes re-opening from a different note actually reorient. **Return to origin (2026-09-19/20, docs/dev/technical-design-return-to-origin.md).** Every file the plugin itself opens goes through `supernote/fileSystem.ts`'s `openPath`, which notifies an observer (registered by `App.tsx`) right before the host call; that stores the path in an in-memory, one-slot record (`storage/returnRecord.ts`, rolled back if `openFile` fails). `reorient()` now asks the pure `domain/returnContext.ts`'s `decideLanding` where to land, in priority order: focus mode, **resume**, the note's enclosing Project/Area, Daily. *Resume* applies when the note open now is the recorded one (paths normalized, record younger than 12 h): the tab shell is left exactly as it was (only `mode` is normalized back to `'tabs'`), and `currentItem` is pointed at the note's Project/Area unless the Current tab is the one on screen. The record is sticky across resumes and is cleared the first time a reopen finds a different note open. Memory-only by decision - a fresh process has no screen state to resume.

**Routing the Lasso button, and the race that fix needed.** The same `registerButtonListener` callback also checks for `LASSO_BUTTON_ID` and sets `mode` straight to `'capture'`. This works because `sn-plugin-lib`'s `PluginManager.registerButtonListener` itself replays the most recent button event (if one arrived within the last second) to a newly-registered listener — the library-level equivalent of the "pending button ID" pattern this kind of plugin architecture usually needs by hand, so no native/`index.js` change was needed for it. That replay does create a real race on a cold start, though: the mount effect's `reorient()` call is async and unawaited, so if the Lasso event replays into the listener *before* `reorient()`'s own awaited calls resolve, `reorient()` finishing afterward would silently overwrite the capture screen with the tab shell. Fixed with a ref (`routedByLassoButtonRef`), set synchronously by the Lasso branch and cleared by the sidebar branch, that `reorient()` checks immediately before either of its own `setActiveTab`/`setMode` calls — and by registering the button listener *before* calling `reorient()`, so a replay lands before `reorient()`'s first `await` can resume. A second ref, `captureNonceRef`, is bumped on every Lasso-button press and used as `CaptureScreen`'s React `key`, forcing a full unmount+remount on each press (rather than a re-render in place) so a second capture while the JS instance is still alive from the first one always re-reads whatever's newly lassoed instead of showing stale state. Unverified on-device: whether a lasso-toolbar press really reports `pressEvent === 3` (logged, not relied on for routing — `event.id` is authoritative since it's assigned in `index.js`), and whether the button's `showType: 1` really auto-shows the plugin view on a Lasso press the same way it does for the sidebar button.

### 2.2 Data model and file format

Every Project/Area folder holds one plain-text data file at its root: `project.txt` (Projects) or `area.txt` (Areas) — `.txt`, not the `.md` the original draft assumed, chosen so the file extension doesn't imply an Obsidian-specific format to anything else that might see it; a plain rename to `.md` restores full Obsidian recognition later if that starts to matter, since the *content* is already Obsidian-flavored Markdown. Identity is the folder itself — no synthetic IDs; renaming the folder in the Supernote file browser *is* renaming the Project/Area, nothing to reconcile.

```
---
kind: project
status: active
dailyFocus: true
---

## Tasks
- [ ] Draft outreach email #next
- [ ] Pay invoice #due:2026-09-05
- [x] Kickoff call
- [-] Cancelled idea → [[Todos/Cancelled idea.note]]

## Meetings
- 2026-09-03 10:00 Kickoff Call → [[Meetings/2026-09-03 - Kickoff Call.note]]
- 2026-09-05 Standup (no time)
```

Parsing/serializing lives entirely in `domain/markdown.ts`, which is deliberately RN/SDK-free (see §3's domain-purity rule). Key facts about the format as actually implemented:

- Checkbox states: `[ ]` open, `[x]`/`[X]` done, `[-]` **cancelled** — Obsidian's own third state, used here as the soft-delete mechanism for *both* Tasks and Meetings (the original draft only specified this for a "delete" concept in the abstract; this codebase extends the same mechanism to Meetings too). A cancelled item's line is never removed from the file — it's just filtered out of the normal view. There's no "show cancelled" UI yet.
- `Task = {text, done, cancelled, tags, dueDate, notePath}`. `tags: string[]` is real now (§2.10): every `#word`/`#word:value` token in `text` is extracted on every parse, lowercased, into `tags` — `text` itself is never rewritten, so a task's `#tags` still live inline in it exactly as typed. `dueDate: string | null` is derived from a `#due:YYYY-MM-DD` tag among those, rather than a separate syntax (`domain/markdown.ts`'s `deriveTaskFields`, also used by UI code to keep an in-memory `Task` consistent the moment `text` is edited, not just on the next file re-parse). `Meeting.tags` is unchanged - still always `[]`, out of scope for §2.10.
- `Meeting = {title, date, time, endTime, days, tags, cancelled, notePath, linkedFile}`. `date` is required (`YYYY-MM-DD`); `time` is `''` for a date-only meeting or a zero-padded `HH:mm`. Every meeting is a one-off: gtdpara has no recurring meetings (every entry is a conscious choice). A hand-written series line (e.g. `every monday 09:00 Standup`) and its indented occurrence lines are not parsed; they are kept as unknown lines and written back untouched.
- **Frontmatter is now partially parsed** (§2.10): `dailyFocus`/`weeklyFocus` booleans, via `domain/markdown.ts`'s `parseFrontMatter`/`writeFrontMatterIntoContent` - the first thing to actually read this block back into a structure since `ensureSkeleton` started writing it. `kind`/`status`/`sortOrder` are still only ever written literally, never parsed - they (and any hand-added key) round-trip as opaque `extraLines`, same "recognized fields first, everything else preserved but reordered to the end" caveat as Tasks/Meetings extra-lines below.
- **Note-linking**: a trailing `→ [[relative/path.note]]` on a Task or Meeting line, extended in this codebase to Tasks as well as Meetings (the original draft only described it for Meetings). See §2.4.
- **Write-through must not clobber hand-added content** — the one rule every parser/serializer function is built around. Only the text span between a `## Tasks`/`## Meetings` heading and the next `## ` heading (or EOF) is ever touched; frontmatter and any other section pass through untouched (`getSpan`/`setSpan` in `markdown.ts`). This is the resolved form of what the original draft flagged as an open question.
- **Known caveat**: a line inside a Tasks/Meetings span that the parser doesn't recognize (a hand-written recurring meeting's occurrence sub-list, or literally anything malformed) is preserved verbatim but always re-appended *after* every recognized line on the next save — its original position relative to the recognized lines is not preserved. Interleaving is lost; content is not.

### 2.3 Data architecture: the cross-project cache

This is the part of the design doc's original §4 ("The cache: disposable, and kept warm two ways") that's now actually built, in `src/storage/dataCache.ts`. It replaced an earlier, narrower `folderIndex.ts` that only cached folder *names*; that file is dead code now (nothing imports it — safe to delete, just not done here since this workflow can't delete files on the device).

```ts
interface CachedItem {
  kind: 'project' | 'area'; name: string; path: string;
  rawContent: string; tasks: Task[]; meetings: Meeting[];
  taskExtraLines: string[]; meetingExtraLines: string[];
  loadError?: string;   // set if this item's file failed to load on the last rebuild
}
interface DataCache {
  scannedAt: number; paths: ResolvedParaPaths; items: CachedItem[];
}
```

One module-level `DataCache | null`, kept current two ways (and, since 2026-09-20, announcing every change to subscribers - see §2.29):

1. **Full rebuild** (`rebuildCache(settings)`) — scans the Projects and Areas folders, then loads every item's own data file, in parallel. Replaces the entire cache on success; one item's load failure is recorded on that item's `loadError` rather than failing the whole rebuild. Triggered manually via Settings → Advanced → "Reload all files" (§2.1), by a Settings save, and by `refreshCache` when it can't work incrementally (below). Since 0.6.0 it also records a `FileStamp` (`exists`, `lastModified`, `size`, one native `statFiles` call) for every data file and `Inbox.txt` before reading them. The Projects/Areas lists also build it on mount when none exists yet.
1a. **Incremental refresh** (`refreshCache(settings)`, 0.6.0, `technical-design-files-0.6.md` §3.2) — what `App.tsx`'s reorient runs, fire-and-forget, on every plugin open or sidebar press. Lists Projects and Areas, stats every data file plus `Inbox.txt` in one call, and re-reads only files whose stamp differs (equality, not "newer") plus new folders; removed folders drop out. A re-read file whose text equals the cached text (gtdpara's own saves don't move the stamp) keeps its old object, so subscribers are notified only on a real change (Inbox changes go through `setCachedInbox`, items through `notifyCacheChanged`). Falls back to a full rebuild when there is no cache, the configured folders differ from `cache.paths` (including an Inbox not yet moved), or `statFiles` is missing. De-duped; a rebuild requested during a refresh waits for it. Logs `refreshCache: n changed, a added, r removed, inbox …`. Known gap: a sync that keeps both time and size is missed until "Reload all files" (help says so).
2. **Write-through** (`updateItemTasks`/`updateItemMeetings`) — every plugin-initiated save (add/toggle/cancel a task or meeting, link a note) updates the matching cache entry in the same operation that writes the file, so every other screen sees the change immediately without needing a rebuild.

**The Inbox in the cache (0.6.0, `technical-design-files-0.6.md` §3.3).** `Inbox.txt` is not an entry of `items` (it is not a Project/Area folder), but the cache module keeps it next to them: `getCachedInbox()`/`setCachedInbox(next | updater)`/`subscribeInbox()`/`reloadCachedInbox(inboxFolder)` (never throws), read through `ui/useCachedInbox.ts` (same screen-activity pattern as `useCachedItems`). `rebuildCache` loads it in parallel with the items; `clearCachedData` drops it. Daily, Planning (Week/Month), Inbox and Review read it from there and write through `setCachedInbox`, so a change on one screen is seen on every other; storage code that writes `Inbox.txt` itself (`itemMove.appendToInbox`, close-out, Google Calendar copy to Inbox) calls `reloadCachedInbox`, Capture hands its `nextInbox` to `setCachedInbox`.

`ensureItemCached(kind, name, path)` is the read-side escape hatch: if an item isn't in the cache yet (cache never built, or built before this folder existed), it loads just that one item's file and — if a cache object already exists — inserts it, rather than forcing a full rebuild to open one Project/Area.

The cache is still fully disposable in the sense the original design intended: a full rebuild always reproduces it correctly from the files, which remain the only real data. What's different from the original framing is the **trade-off window got wider**: before this cache existed, every screen open (Home's folder scan, ItemDetail opening a Project/Area, Daily's aggregation) did its own fresh filesystem read, so "an edit made outside the plugin" was visible the next time you opened *anything*. Now, a screen can serve cached data that's stale relative to an external edit until the next automatic or manual rebuild. This is a deliberate trade for the responsiveness Daily view needed (see §4's note on this) — worth knowing before assuming "opening a screen always shows the latest file contents," which was true before and isn't quite true anymore.

`storage/dailyAggregate.ts`'s `buildDailyAggregate(items, now)` is a pure, synchronous transform over `DataCache['items']` — zero filesystem I/O — used by Daily view. It is the model for how any *future* cross-project feature should be built: read the already-warm cache, don't re-scan the filesystem yourself.

### 2.4 Linked notes

`storage/noteLinks.ts` creates the `.note` file a Task or Meeting's `notePath` points to, inside a `Todos/` or `Meetings/` subfolder sibling to the item's own `project.txt`/`area.txt`. Naming: a meeting's note is `"<date> - <title>.note"`; a todo's is just its sanitized text; a collision appends `" (2)"`, `" (3)"`, etc. Every linked note is created with the fixed template name `style_white` (Supernote's built-in blank page) — **not** picked at runtime from `PluginCommAPI.getNoteSystemTemplates()`'s `vUri`/`hUri` fields, which are resource references `PluginFileAPI.createNote` doesn't resolve; passing one produces "Background template file does not exist." This matches the working pattern from the textboxHelper project's import flow, which creates notes the same way.

### 2.5 Time and date handling

All in `domain/meetingTime.ts`, pure and RN-free:

- `parseFlexibleTime`: blank is valid (no time at all); a bare 1–2 digit hour defaults minutes to `00` (`"8"` → `08:00`); `H:mm`/`HH:mm` requires an *exactly* two-digit minute — a single digit after the colon (`"8:5"`) is rejected as a likely truncated entry, not silently zero-padded.
- `meetingTimestampMs`: a date-only meeting dated *today* sorts as the very last thing today (`23:59:59`) rather than the first (`00:00`) — it reads as "sometime later today," staying upcoming for as long as today lasts and sorting after every timed meeting today. A date-only meeting on any other date still sorts as `00:00` that day (this only affects same-day ordering against another entry on that exact date, never the upcoming/past split).
- `splitAndSortMeetings`: upcoming meetings ascending (soonest on top), past meetings descending (most recent on top) — the add-input sits between the two groups in `ProjectDataPanel`.
- New meetings prefill today's date (`todayIso`); `isoDateOffset(days, now)` (used for "tomorrow" in Daily view) is calendar-based, not `+86400000`ms, so it can't be shifted onto the wrong day by a DST transition.

### 2.6 Styling

`src/ui/theme.ts` exports the app's *only* sanctioned font sizes:

```ts
export const FONT = {large: 22, medium: 17, small: 15} as const;
```

Every screen imports `FONT` rather than hardcoding a `fontSize`. This exists specifically so the whole app can be nudged larger/smaller from one place, and so nobody introduces a fourth size by accident — see §3's styling rules.

**Target device (2026-09-07).** This app is built and tuned against one specific device, the Supernote A5 X: 10.3" E Ink, 1404×1872 physical pixels, 226 PPI. `FONT`'s values are React Native dp, not raw device pixels, and the exact dp-to-physical-pixel ratio the Supernote host reports hasn't been independently confirmed — so this is a fact to reason from, not a precise "N px = M characters" conversion yet. In practice this project has always tuned fixed-width things (pagination page sizes, §3's PAGE_SIZE note; the due-date field's width, ui/TaskQuickAdd.tsx) as starting-point guesses, checked and adjusted after looking at the real device, rather than computed up front - the same "never measure layout at runtime, retune the constant instead" posture ui/pagination.ts's own doc comment already explains for page sizes. The concrete lesson from one such guess-wrong (`dueInput`'s width sized too small to show a full `YYYY-MM-DD` date, showing only `MM-DD`): before fixing a text field's width, sanity-check it against the *longest* real value it needs to hold in full (a date string, the longest chip label, etc.), not just against what looks reasonable on screen.

**On-screen keyboard/handwriting panel height (2026-09-07).** When the device's text-input panel (on-screen keyboard, or its handwriting-recognition equivalent) is raised, it covers roughly the bottom third of the screen - the user marked its top edge on a real device screenshot at approximately 65% down the full screen height (so, on the A5 X, the panel covers roughly the bottom ~650 physical px of the 1872px height). This is an eyeballed on-device mark, not a measured/confirmed constant - treat it as "assume nothing below ~65% of screen height is visible or reachable while a text field has focus" until it's checked more precisely, the same starting-point posture as `FONT`/`PAGE_SIZE`/field widths above. §3's styling rules turn this into a placement rule: keep text inputs, and anything a user needs to see or tap *while* typing (a Save/Cancel button, a validation error), above that line - `ui/TaskQuickAdd.tsx`'s existing "quick-add sits above the list" placement already does this by accident (moved there in the 2026-09-03 Daily-cleanup pass for a different reason - staying clear of the keyboard overlap), but it hasn't been an explicit, named constraint until now.

### 2.7 Settings and persistence

Two completely separate persistence mechanisms, deliberately not unified:

- **Plugin configuration** (`storage/settingsStorage.ts`) — the base root and the four folder names, in `AsyncStorage` under one JSON key. This is plugin-internal, not PARA content; nobody needs to hand-edit it outside the plugin, so `AsyncStorage` is the right tool.
- **PARA content** — every Task, Meeting, and linked note lives as a real file under the configured roots (`domain/settings.ts`'s `resolvePaths`), per §2.2. This is the only thing the "files are the source of truth" vision applies to.

`resolvePaths` also resolves the Inbox: `inboxFolder` (`<areas>/<inboxFolder setting>`, default `2 Areas/0 Inbox`) and `inbox` (`<inboxFolder>/Inbox.txt`); see §2.38 — the Inbox is addressed through the cache's paths, which carry its *effective* location.

### 2.8 Permissions

`supernote/pluginPermissions.ts` wraps the host's `hasPermission`/`requestPermission` calls with an 8-second timeout. This exists because the host's permission bridge has been observed to simply never resolve on some builds — no dialog, no rejection — which without a timeout looks like the plugin silently doing nothing (this was the leading early hypothesis for the original "+Add does nothing" bug, before the real cause — a keyboard/tap-focus interaction, see §3 — was found). A host with no runtime permission API at all is treated as pre-granted rather than blocked forever.

Permissions and deletes (`technical-design-inkhub-submission.md`): declared permissions are FILE:READ, FILE:WRITE, FILE:DELETE and INTERNET. The host intercepts *every* file and network access the same way - sn-plugin-lib, Android/RN APIs and our own Kotlin modules alike - so each call site checks its permission right before use (`listFolderEntries` included). FILE:DELETE is requested only after a confirmation that names what is deleted (`ensureFileDeletePermission(description)`); the only deletes are `deleteEmptyFolder` (native: empty folders only) and `deleteTempTree` (native: only inside the plugin's private temp folder, `getPrivateTempDir`, which needs no permission). The PDF writer builds into that private folder and copies the finished file out; the debug log rotates by overwriting. Host-call diagnostics (`recordDebugLogEntry`) are log lines, not files.

### 2.9 Lasso capture and Inbox

(The capture screen itself is described as it is today in §2.41; the paragraphs below are about the Inbox and the earlier capture design.)

`screens/CaptureScreen.tsx`, reached via the Lasso-toolbar button routing in §2.1. On mount it reads the active lasso selection (`supernote/lasso.ts`'s `getLassoElements`/`getPageDisplaySize`/`recognizeElements` — thin wrappers around the matching `PluginCommAPI` calls, with no file-permission requirement since these are comm/UI calls, not file I/O) into an editable text field; a host-side recognition failure resolves to `''` rather than throwing, since typing the text by hand is always the fallback. The user then manually picks Todo or Meeting (no auto-detection from the recognized text — deliberately, handwriting recognition is too unreliable to guess the type from), a destination — always the current note's enclosing Project/Area via the same `findEnclosingItem` call `App.tsx` uses, or Inbox if it has none, with no way to override it (§2.20 retired the inline expandable destination picker this paragraph used to describe) — and an off-by-default "🔗 Link to source note" checkbox. Saving a Project/Area destination goes through `ensureItemCached` + `saveTasks`/`saveMeetings` + `updateItemTasks`/`updateItemMeetings`, the same write-through pair every other mutation uses (§3); saving to Inbox uses the same `saveTasks`/`saveMeetings` functions with `kind: 'inbox'`. After a successful save, `setLassoBoxState(2)` clears the native lasso (cleanup only, never fatal to the capture); cancelling leaves the lasso alone, so the user can still act on it via Supernote's own lasso toolbar.

**Inbox** (`Inbox.txt`, directly under the base root up to 0.1.0, since §2.38 in its own folder `2 Areas/0 Inbox` — `domain/settings.ts`'s `resolvePaths`) uses the exact same `GtdParaFile` Tasks/Meetings markdown shape as `project.txt`/`area.txt` — `storage/projectFile.ts`'s `dataFileName`/`loadProjectFile`/`saveTasks`/`saveMeetings` all take `GtdParaKind` already, so `kind: 'inbox'` with `itemPath` = the Inbox folder just falls out of the existing machinery (`domain/markdown.ts`'s `ensureSkeleton` was widened from `'project' | 'area'` to the full `GtdParaKind` for this — frontmatter now reads `kind: inbox`). Inbox.txt is deliberately **not** part of `storage/dataCache.ts`'s `items` array — it's a single flat file, not a Project/Area folder `rebuildCache` scans — so both consumers below load it directly (`loadProjectFile('inbox', paths.inboxFolder)`), with no write-through cache entry to keep in sync. Filing an Inbox item into a Project/Area (`storage/inboxFiling.ts`'s `fileInboxTask`/`fileInboxMeeting`, plus §2.20's shared `resolveFilingPick` mapping) is reachable from exactly two places: the dedicated Inbox tab (§2.16) and the Review tab's Inbox-to-zero step (§2.13) — both arm the same `ui/FileBrowserPane.tsx` Files pane, the same mechanism Project↔Area assignment (§2.19) uses to pick an Area, rather than either screen keeping its own picker (§2.20). Daily view's Inbox-sourced rows (§2.11) can be edited, toggled, and linked like any other row but were never a filing surface themselves; Daily's own Inbox *section* is gone regardless (§2.16), superseding this section's original "stays exactly this minimal on purpose" framing.

**Linking to an arbitrary source note** (CaptureScreen's checkbox above) needed a small, backward-compatible extension to how `notePath` is resolved. Every `notePath` a *linked note* created via `storage/noteLinks.ts`'s `createLinkedNote` produces is relative to its own item's folder (`Todos/foo.note`), which only works because that note lives inside the destination folder. A capture's source note isn't necessarily anywhere under the destination folder (or under any Project/Area at all, when the destination is Inbox), so relative-path math across arbitrary folders doesn't apply. Rather than force that case into the relative convention, `noteLinks.ts`'s new `resolveNotePath(itemPath, notePath)` treats a `notePath` starting with `/` as an absolute path and uses it as-is; anything else resolves relative to `itemPath` exactly as before. No `notePath` created before this ever started with `/`, so existing data keeps working unchanged. `ProjectDataPanel`'s two "open note" handlers were switched to `resolveNotePath` so this covers a linked-back-to source note the same way it covers a plugin-created linked note.

### 2.10 Daily/weekly focus

Lets the user pick a capped number of Projects/Areas as "focus" for today, and separately for the current week, and uses the daily pick to decide which tasks show on Daily view.

**Data model.** Two additions to `domain/types.ts`'s `Task`, both derived from `text` on parse — never a second source of truth:

- `tags: string[]` — general `#tag` extraction (`domain/markdown.ts`'s `TAG_RE`), no longer always `[]`. Covers GTD flow-state tags (`#next`), context tags (`#alice`, `#team-jf`), and the due-date tag below, all through the "one tag mechanism" the `Task` doc comment describes — deliberately not separate fields/syntaxes per tag kind.
- `dueDate: string | null` — `YYYY-MM-DD`, derived from a `#due:YYYY-MM-DD` tag (`DUE_TAG_RE`) if present, else `null`.

`domain/markdown.ts` exports `deriveTaskFields(text): {tags, dueDate}` as the one place both fields are computed; UI code calls it immediately on every edit to `text` (`ProjectDataPanel`'s `handleAdd`/`commitEdit`, `CaptureScreen`'s two save paths) so `tags`/`dueDate` are never stale even before the next reload. `Meeting.tags` was untouched by this work (later derived from the title, §2.23).

Frontmatter is parsed for the first time ever in this codebase — previously write-only (`ensureSkeleton` wrote a literal string, nothing read it back). `markdown.ts`'s `getFrontMatterSpan`/`setFrontMatterSpan` mirror the existing `getSpan`/`setSpan` span-scoped pattern, scoped to the `---`...`---` block; `parseFrontMatter(content): ParsedFrontMatter` reads `dailyFocus`/`weeklyFocus` booleans (plus any unrecognized lines, preserved verbatim like every other parser's extra-lines handling — same reordering caveat as §2.2 applies) and `writeFrontMatterIntoContent(content, dailyFocus, weeklyFocus, extraLines)` writes them back, omitting a `dailyFocus: true`/`weeklyFocus: true` line entirely when false rather than writing `false`, so an unfocused item's frontmatter stays clean. `ProjectFileState` (loaded) and `CachedItem` (cached) both gained flat `dailyFocus: boolean; weeklyFocus: boolean; frontMatterExtraLines: string[]` fields, matching how Task/Meeting extraLines are already flat fields rather than nested under a `frontMatter` object — see the `FrontMatter` doc comment in `domain/types.ts`.

**Storage.** `storage/projectFile.ts`'s new `saveFrontMatter(kind, itemPath, rawContent, dailyFocus, weeklyFocus, extraLines)` mirrors `saveTasks`/`saveMeetings` exactly (`ensureSkeleton` → `writeFrontMatterIntoContent` → write file → return next content). `storage/dataCache.ts`'s new `updateItemFrontMatter(...)` is the matching cache write. `storage/focusSlots.ts` is a new file centralizing every slot-limit rule so the two UI surfaces below can never disagree about what's allowed: `countFocused`/`canAddFocus`/`focusBlockedReason` (kind × scope aware, reading the matching count from `GtdParaSettings`) and `setItemFocus(item, scope, value)`, which does the write-through pair (`saveFrontMatter` then `updateItemFrontMatter`, file first) and returns the updated state for the caller to merge into its own local state.

**Aggregation rule (narrowed 2026-09-10, docs/dev/technical-design-daily-todo-filter.md).** `storage/dailyAggregate.ts`'s `buildDailyAggregate` now filters tasks instead of listing every open task flat (deliberate behavior change from the historical "flat" Daily view — see §5): an open (`!done && !cancelled`), non-shelved (not Someday/Maybe; Waiting For has its own rule — see §2.14) task shows if `dueDate !== null && dueDate <= tomorrowDate` (today, tomorrow, or overdue — a single comparison covers all three, since any earlier date is also `<= tomorrowDate`), **or** it's `flowState === 'next'` **and** its `CachedItem.dailyFocus` is true. This is a further narrowing from the rule this paragraph originally described: previously *any* open task belonging to a daily-focused Project/Area showed here regardless of its own tags, and `#next` alone (regardless of focus) was also enough on its own — a busy focused project could flood Daily either way. Now focus only ever surfaces that item's own `#next` task(s), never everything it has open, and a `#next` task with no due date needs its item to be daily-focused to show at all. Inbox is a carve-out: its `#next` tasks keep showing unconditionally (no Project/Area to be "in daily focus" for), only the due-date leg widens to match. A `#next` task that falls out under this narrower rule doesn't just vanish unaccounted-for — `storage/reviewAggregate.ts`'s `unfocusedNextItems` bucket surfaces it on a dedicated Weekly Review step (§2.13) with a one-tap "Add to Daily focus" action plus per-task Someday/Maybe/Done/Cancel actions. Meetings are unaffected by any of this.

**Settings.** Four new independent counts on `GtdParaSettings` (`dailyFocusProjectCount`/`dailyFocusAreaCount`/`weeklyFocusProjectCount`/`weeklyFocusAreaCount`; defaults 3/2/5/3), editable in `Settings.tsx`'s new "Focus slots" section. Lowering a count below how many items are currently focused does **not** un-focus anything — over-limit items stay focused until manually removed (§2's "Recommended" answer during design), which is why `focusBlockedReason` only blocks *adding*, never reports an over-limit state as an error.

**UI.** Two touch points, both going through `focusSlots.ts` so the limit logic is never duplicated:

- `ProjectDataPanel`'s new `FocusSection` — two checkboxes, "Daily focus"/"Weekly focus" (the user's explicit choice over a combined picker), each calling `toggleFocus(scope, value)`; turning one on checks `focusBlockedReason` first and surfaces the block message inline rather than silently no-opping.
- `DailyView`'s new Focus section (daily scope only — weekly focus isn't editable here, since nothing consumes weekly focus yet) — `DailyFocusKindSection`, one per kind (project/area), lists every currently-focused item of that kind with a "✕" to remove, followed by `limit - focused.length` empty "+ Add" slots that expand into a candidate picker of non-focused items of that kind to fill the freed slot. **Superseded by §2.22** (2026-09-10): `DailyFocusKindSection`'s inline-expanding candidate list is gone, replaced by `ui/DailyFocusPanel.tsx`'s arm-and-pick mechanism; the fixed-slot ✕/+Add display itself lives on unchanged, as that panel's own Focus tab.

**Verified** via `verify-markdown.ts` (tag extraction, due-date derivation, frontmatter round-trips, extra-line preservation) and `verify-aggregate.ts` (the new Daily filter rule, `focusSlots.ts`'s counting/limit functions) — both standalone scripts per §3's verification convention — plus a full `tsc --noEmit` pass and `eslint` against the real project config.

### 2.11 Daily view: two-column layout, inline edit/note parity, quick-add

Requested as a Daily-view usability pass once §2.10's focus filter had been living there a while: the flat, read-mostly screen needed to hold more without needing ItemDetail as a detour for every edit.

**Layout.** Below the header, two stacked blocks: a two-column middle row (Calendar left, Open tasks right), and a two-column Focus row (Projects | Areas — the same `DailyFocusKindSection` from §2.10, just placed side by side instead of stacked). Only the middle row scrolls, and each of its two columns scrolls independently (its own `ScrollView`, bounded to the row's height) — a long Open-tasks list never pushes the Calendar column around and vice versa. The Focus row is left unscrolled on the assumption it stays short by nature (the configured slot counts, §2.10). Inbox no longer has its own block here at all — see §2.16: since 2026-09-03 it's a full standalone tab, and its qualifying tasks/meetings surface inside these same Calendar/Open-tasks columns instead, one "Inbox" source among the others. **Superseded by §2.22** (2026-09-10): the full-width Focus row is gone; a narrower Focus/Projects/Areas panel now sits directly below Calendar, inside the left column, and Open tasks (right column) keeps the full row height that used to be shared with Focus.

**Calendar column.** Same meetings-today-and-tomorrow data as before (`buildDailyAggregate`, §2.10). Originally grouped under two small always-both-visible "Heute"/"Morgen" headers; since §2.15 that's a `calendarDay: 'today' | 'tomorrow'` toggle instead (two small `Pressable`s, only one day's meetings rendered at a time) — Open Tasks stays one unified list, this toggle is Calendar-only. Each row shows just the time (or nothing, for a date-only meeting) and the title. Since `buildDailyAggregate`'s meetings are already sorted soonest-first and every today-timestamp sorts before every tomorrow-timestamp (`meetingTimestampMs`'s today-sorts-at-23:59:59 rule, §2.5), filtering to one day is a plain filter of the already-sorted array, not a second sort.

**Open tasks column.** Originally one flat list; since §2.15 it's grouped by source Project/Area (`storage/dailyAggregate.ts`'s `groupDailyTasksByItem` — daily/weekly-focused items' groups float first, via the same shared `isFocused` §2.12 already exports from `domain/destination.ts`). The group header (the Project/Area's name) is now the row's *only* "jump to that item" affordance — see Edit/note parity below for what it replaced.

**Edit/note parity.** Meetings and Open-tasks rows gained the same inline edit (tap the row text), cancel (✕), and note create/open (📓/+📓) actions `ProjectDataPanel`'s Todos/Meetings sections already had. Originally, tapping a row's item-name subtext was the "jump to that Project/Area" action (since tapping the main text starts an edit); since §2.15 that per-row subtext is gone from Open-tasks rows specifically (redundant under the new group header above) — Calendar rows keep it, since meetings aren't grouped by item. The wrinkle versus `ProjectDataPanel`: a Daily-view row can belong to a *different* Project/Area than the row next to it, so every save re-fetches that entry's own source item from the cache by path before mutating it. `DailyView.tsx`'s new `saveEntryTasks`/`saveEntryMeetings` generalize what used to be `handleToggleDone`'s own one-off version of this (fetch by `entry.item.path` → mutate at `entry.taskIndex`/`entry.meetingIndex` → `saveTasks`/`saveMeetings` → `updateItemTasks`/`updateItemMeetings`, file first, same write-through order as everywhere else) so toggle, edit, cancel, and note-linking all share one path. **Inbox now gets full parity too** (§2.16, superseding this paragraph's original "deliberately excluded" note) — Inbox-sourced rows here render through the same shared `ui/TaskRow.tsx`/`ui/MeetingRow.tsx` components the new Inbox tab uses, `DailyItemRef.kind` having been widened from `'project' | 'area'` to the full `GtdParaKind` and `basePath` substituting for `itemPath` when saving.

**Quick-add.** Each column gets an add block at the **top** of its `ScrollView` (moved there from the bottom in §2.15 - it used to sit behind the on-screen keyboard on a list of any real length): free-text (tags/due-date typed inline, same "one tag mechanism" as everywhere, §2.10) for a task, title/date/time for a meeting, both always saved straight to Inbox with no destination picker at all (§2.20 retired the picker both quick-adds used to show here; a Daily-view quick-add never had a "current note" context to smart-default from anyway, unlike `CaptureScreen`, whose own picker is likewise gone). A meeting added for a date other than today/tomorrow saves fine, it just won't show here until then; the meeting quick-add's date field now defaults to whichever of Today/Tomorrow is currently selected (§2.15) rather than always today.

**New shared modules, pulled out rather than duplicated a third time.**

- `domain/destination.ts` — the `Destination` type plus `destinationLabel`/`sameDestination`, originally moved out of `CaptureScreen.tsx` so its (then-overridable) Lasso destination picker and Daily view's own quick-add picker couldn't drift on what counted as "the same destination." Both of those pickers are gone as of §2.20, but the type and helpers stayed live: `storage/dailyAggregate.ts`, `screens/ItemsList.tsx`, and `ui/GoogleCalendarPanel.tsx`'s own copy-destination picker (§2.17) all still depend on them for unrelated reasons.
- `domain/meetingTime.ts`'s `validateMeetingFields` (+ `MEETING_DATE_RE`) — moved out of `ProjectDataPanel.tsx`, which now imports it too, so its Meeting add/edit forms and Daily view's new ones run the exact same title/date/time validation.

### 2.12 Project/Area status & Archive

A lifecycle status per Project/Area (Active/On Hold/Done — Projects; Active/On Hold — Areas), plus an "Archive" action that physically moves the folder into the configured Archive folder. Sits alongside §2.10's focus feature as a second orthogonal axis on the same frontmatter block, not a replacement for it. Full requirements/design history: `technical-design-status-archive.md` in this same `docs/` folder.

**Data model.** `domain/types.ts`'s new `ItemStatus = 'active' | 'on-hold' | 'done' | 'archived'` — one type for both kinds; the UI restricts which values each kind's status picker *offers* (Areas never see "Done"), but the parser accepts any of the four regardless of kind, same "never invent structure, never clobber what's there" stance as every other parser rule here. `FrontMatter.status`'s type widens from the old `'active' | 'archived'` to this.

`markdown.ts`'s `ParsedFrontMatter`/`parseFrontMatter`/`writeFrontMatterIntoContent` gain `status` alongside the existing `dailyFocus`/`weeklyFocus` fields — same span-scoped frontmatter mechanism §2.10 built, extended rather than duplicated. Unlike the focus flags (omitted when `false`), `status` is always written, since it always has a meaningful value; an unrecognized or missing `status:` line defaults to `'active'` rather than throwing. `ensureSkeleton`'s literal `status: active` skeleton line needed no change — it already matches what the new parser recognizes.

**Storage.** `projectFile.ts`'s `saveFrontMatter`/`ProjectFileState`, `dataCache.ts`'s `CachedItem`/`updateItemFrontMatter`, and `focusSlots.ts`'s `setItemFocus` all widen to carry `status` alongside the two focus flags — one frontmatter write covers a status change and its focus side-effect together (below), never two separate file writes for one logical change. A new `storage/statusControl.ts` holds `setItemStatus(item, next)` for the plain Active/On Hold/Done picker — deliberately excludes `'archived'` from what it can write; reaching Archived always goes through:

`storage/archive.ts`'s `archiveItem(item, settings)` — moves the folder (via the new `supernote/fileSystem.ts` `moveFolder`, backed by a new native `GtdParaFileModule.kt` method, `File.renameTo()`; same volume as source and destination, so no cross-filesystem copy is needed), then stamps `status: archived` into the file at its *new* location, then removes the item from the cache (`dataCache.ts`'s new `removeCachedItem`). The frontmatter write and the physical move are kept coupled in this one function on purpose — decoupling them would let a folder sit in `Projects/` marked `archived` while the app still treats it as a normal, present item. If the post-move frontmatter stamp fails, the move itself has already succeeded (the part that matters for the one-way-door behavior below) and the failure is just logged, not rolled back.

**Archive layout superseded (2026-09-28, §2.32).** Archived folders no longer land flat in `Archive/`. They go to `Archive/<year>/[<Area>/]<name>/`, where the year is the Project's `doneAt` (or today for Areas). An Area archive merges into its year folder via `moveFolderMerge`, and `archivedAt` is stamped next to `status: archived`. `archive.ts`'s `archiveTargetsFor` is the single place that computes the target. For Projects, the Archive button now opens the close-out wizard (full or quick) instead of archiving directly.

**Focus interaction.** Only Active items can hold a focus slot: `setItemStatus` clears both `dailyFocus`/`weeklyFocus` in the same write whenever the new status isn't `'active'` (On Hold and Done both clear it — a deliberate choice, not just On Hold, so a finished project doesn't keep occupying a scarce slot). `DailyView`'s focus-candidate filter and both destination pickers (below) now also require `status === 'active'` — closing the open question §2.10 left about whether archived items should be excluded from the focus picker, and extending it to On Hold/Done.

**Destination pickers.** `domain/destination.ts` gains `destinationCandidates(items)`: filters to Active only, then floats currently-focused items to the top (stable sort, so the rest keep their existing alphabetical order) — originally used by both `CaptureScreen.tsx` and `DailyView.tsx`'s quick-add, which previously each did their own unfiltered `items.filter(kind === ...)`. Both of those call sites are gone as of §2.20 (Capture auto-resolves its destination now; Daily's quick-adds always go to Inbox), leaving `ui/DestinationPicker.tsx`'s own use inside `ui/GoogleCalendarPanel.tsx` (§2.17) as `destinationCandidates`'s one remaining live caller. `ItemsList.tsx`'s own Active section applies the same focused-first ordering for consistency, even though nothing there needed the Active-only filter (it already groups by status — see below).

**UI.**

- `ItemsList.tsx` — was a flat, ungrouped list; now three (Projects) or two (Areas) labeled sections — Active, On Hold, and (Projects only) "Done — awaiting review" — all shown by default, a group with nothing in it simply omitted. A focused item gets a "★ " prefix, and an item with an abbreviation shows it after the name (`Acme Tender #ATR ›`, smaller and not bold). Rows use 8 px vertical padding (38 px per one-line row) - a little more than Review's item lists, which share `ui/itemEntryRow.ts` with its defaults (no abbreviation, 6 px) through an `ItemEntryOptions` argument. Archived items are never in this list at all, since their folder isn't under `Projects/`/`Areas/` any more.
- `ProjectDataPanel.tsx` — originally held a `StatusSection` (a 3-way or 2-way pressable-pill picker) above its `FocusSection` plus an `ArchiveAction` below both; as of §2.16 (2026-09-03) both moved out into `ui/ItemStatusPanel.tsx`, rendered by `ItemDetail.tsx` in the left pane below Files rather than inline in this panel. `FocusSection` itself stays in `ProjectDataPanel.tsx` and still takes a `disabled` prop (true whenever status isn't Active) — greyed out with a one-line explanation rather than hidden outright, since an On Hold/Done item is still fully present in the app, unlike an Archived one; `ProjectDataPanel` still loads `status` itself for exactly this check, even though it no longer renders the status picker.
- `ui/ItemStatusPanel.tsx` (§2.16) — the 3-way/2-way status-pill picker and the "🗄 Archive…" bordered button (native `Alert.alert` confirmation, folder names pulled from the user's actual Settings, calling `archiveItem` on confirm), extracted from `ProjectDataPanel.tsx` into their own component with its own independent `ensureItemCached` load (the "extract, don't lift" pattern — see §2.16) so `ItemDetail.tsx` doesn't need to become a second owner of item data.
- `ItemDetail.tsx`/`App.tsx` — the `onArchived` callback now originates from `ui/ItemStatusPanel.tsx` (previously `ProjectDataPanel`) and threads up through `ItemDetail` to `App.tsx` the same way, which clears `currentItem` and switches back to the Projects/Areas tab the item came from once its folder has actually moved — `currentItem.path` stops resolving to anything real at that point.

**Archive is a one-way door**, matching §2.1's existing "Resources/Archive are hidden and not scanned at all" decision rather than reopening it: no restore/browse-Archive UI anywhere in the plugin. Bringing an item back means moving its folder by hand in Supernote's own file browser.

**Verified** via a scoped `tsc --noEmit` pass (strict mode, hand-written shims for `sn-plugin-lib` and the untouched neighboring modules) covering every file this feature touched — clean, no errors. **Not yet verified on-device**: the new native `moveFolder` Kotlin method hasn't been built/run on a device or emulator from this session (no on-device build access here) — worth a dedicated on-device smoke test (archive a throwaway test Project, confirm the folder actually lands in Archive/ with the right name, and that a same-name collision is rejected rather than silently overwriting) before relying on it. The standalone-Node-script verification §3 calls for (mirroring `verify-markdown.ts`/`verify-aggregate.ts`) for `parseFrontMatter`'s new `status` field/round-trip and `destinationCandidates`'s filter+sort hasn't been written yet either — the existing scripts should be extended with the new cases rather than a third script started fresh.

### 2.13 Weekly Review

A 10-step (9 until 2026-09-20, when "Meetings to close out" was inserted after Week ahead - see §2.27; the numbered list below still shows the original 9, so read every step number after "Week ahead" as +1), step-by-step wizard on its own tab (`screens/ReviewScreen.tsx`), designed to keep integrity around Projects/Areas/Meetings/Tasks by walking through every place things quietly go stale — one step at a time, with cleanup actions right there on the spot, not a report to act on afterward. Requirements were clarified in chat before any design work, then screen mockups (Claude Design canvas) were reviewed and iterated before implementation, per this project's own standing workflow.

**Interaction with flow-state tags (§2.14, added 2026-09-02).** Originally this feature shipped with "task tags are explicitly out of scope; nothing here reads or writes them" — no longer true. Every `TaskQuickAdd` on this screen (the Week-ahead step's look-ahead, and each stalled/neglected card) composes flow-state/due/waiting-on tags exactly as Daily view's does, since it's the same shared component. More significantly, §2.14's flow-state work changed what "stalled"/"neglected" *means*: `buildReviewAggregate` now excludes Someday/Maybe tasks from the "has open work" check (a project whose only open tasks are shelved to Someday/Maybe reads as stalled, same as one with no tasks at all — Waiting For tasks still count as open work, since they're blocked, not shelved), and each stalled/neglected card surfaces those excluded tasks directly (`ReviewProjectEntry.shelvedTasks`) with a one-tap "→ Next" button, so discounting them from the stalled check doesn't mean hiding them. Reinstating the other tag-dependent Review ideas floated during §2.14's design (e.g. a dedicated Waiting-For follow-up step) was explicitly decided against for now — out of scope until asked for.

**The 9 steps, in order:**

1. **Overview** (added 2026-09-02, documented here 2026-09-10 — a pre-existing doc gap, not introduced by this round) — shows `settings.lastReviewCompletedAt` (hand-rolled "today"/"yesterday"/"N days ago"/short-date via `formatCompletedAt`) and, if present, the *previous* completed review's `settings.lastReviewSummary` as a flat bullet list (`summaryLines()`, one line per non-zero counter) — a deliberately coarse, purely motivational recap ("2 stalled projects activated, 4 tasks added…"), not an audit trail (`domain/settings.ts`'s `ReviewSummaryCounts`). Counters are a plain running tally bumped inline at each relevant action's success point across every other step (`tasksAdded`, `inboxCleared`, `reactivated`, `onHold`, `markedDone`, `archived`, `weeklyFocusAdded`, `dailyFocusAdded`), except `projectsActivated`/`areasActivated`, computed once at "Finish review" time by checking which stalled/neglected cards still on screen ended up with an actionable open task. Read-only otherwise — no actions live on this step itself.
2. **Week ahead** — an `ui/TaskQuickAdd.tsx` block (fixed to Inbox, no destination picker — §2.20) at the top, then a compact 7-day list (today through +6) of every not-cancelled meeting in that window, grouped under a "Today"/"Tomorrow"/"Wed 9/4"-style heading per day. Deliberately minimal per day: just `{title} — {Project/Area name}`, no times, no note-link affordance, no edit/cancel — this step is a fast read-only look-ahead, not a meeting editor (that's still `ProjectDataPanel`/Daily view's job). Comes *before* Inbox to zero (next), not after, since a meeting glanced at here sometimes surfaces a task that belongs in Inbox.
3. **Inbox to zero** — every open Inbox task/meeting, since §2.20 laid out as a two-pane screen matching the Inbox tab's own shape: a left-side Files pane (`ui/FileBrowserPane.tsx`, Projects/Areas/Resources tabs) and, on the right, Tasks above Meetings through the shared `ui/TaskRow.tsx`/`ui/MeetingRow.tsx` components — full inline edit, note create/open, File, and (new as of §2.20) Link, alongside Done (tasks) / Cancel (both). Tapping a row's File action arms the Files pane restricted to just the Projects/Areas tabs (Resources structurally excluded — an Inbox item can never be filed into Resources) with `pickKind: 'folder'`, so tapping a Project/Area folder at the top level completes the move immediately without drilling in; the move itself still commits through `storage/inboxFiling.ts`, via the new shared `resolveFilingPick` mapping (§2.20). This replaces the step's original inline compact list, `ui/FileToPicker.tsx`, now unused by any screen (§2.20). Done/Cancel mutate the Inbox task/meeting in place, same soft-delete convention as everywhere else. Any action that closes out the item removes the row from this step's list (filtering on `!done && !cancelled`, or having left Inbox entirely for File) — the point is watching the list shrink to zero.
4. **Stalled projects** — every Active project with zero *actionable* open tasks (Someday/Maybe don't count — see §2.14; `storage/reviewAggregate.ts`'s `buildReviewAggregate`): name (tap to jump to it), a hint, its next 2 upcoming meetings if any exist (any date, not bounded to the 7-day window above — a stalled project's only near touchpoint might be three weeks out), its live open-tasks list, any shelved Someday/Maybe tasks with a one-tap "→ Next" promote button, a fixed-destination `TaskQuickAdd`, and 3-way status pills (Active/On Hold/Done) plus Archive. This card list is frozen per step-visit (see "Resume behavior" below) — adding a task or promoting a shelved task never makes the card disappear early; only an explicit status-change/Archive action does.
5. **Done awaiting review** — every project at status Done: Reactivate or Archive. No status pills here (unlike step 4/6) — these are discrete actions, since Archive is a physical folder move (`storage/archive.ts`), not a plain frontmatter change.
6. **On Hold reconsideration** — every Project *and* Area at status On Hold, together (kind-labeled): Reactivate always available, "→ Done" only for Projects (Areas never reach that status), Archive always available.
7. **Neglected areas** — the Areas counterpart of step 4: same card shape (including the frozen-per-visit list and live open-tasks/shelved-task recompute), but a 2-way status choice (Active/On Hold only) since Areas never reach Done.
8. **Unfocused next items** (added 2026-09-10, docs/dev/technical-design-daily-todo-filter.md) — every Project/Area not currently in *daily* focus (regardless of status) that has at least one open `#next` task, i.e. exactly the items whose `#next` tasks no longer qualify for Daily view under §2.10's narrowed rule (`storage/reviewAggregate.ts`'s `unfocusedNextItems`, built via the exported `nextTasksFor` helper). Each card lists those `#next` tasks individually with its own row of per-task actions (→ Someday, → Maybe, Done, Cancel — "deleted" maps to Cancel, since the app has no true delete, same soft-delete convention as everywhere else), plus one whole-item "Add to Daily focus" button (going through `storage/focusSlots.ts`'s usual `focusBlockedReason`/`setItemFocus`, same as §2.10's other focus touch points — blocked inline, same message, if the relevant daily slot count is full). Taking any per-task action removes just that task's row; once an item's last `#next` task is resolved the whole card drops out. Like Stalled/Neglected, this step's card list is frozen per step-visit.
9. **Weekly focus reset** — two columns (Projects | Areas), each a focus-slot picker built the same way Daily view's own daily-focus section works (`storage/focusSlots.ts`), just `scope: 'weekly'` and the `weeklyFocus*Count` settings instead of daily — this is the first real consumer of weekly focus (domain/settings.ts's own note that it was "reserved for a future week view"). Ends with a "Finish review" button — the *only* action that writes `settings.lastReviewCompletedAt` (below); merely stepping through every screen does not count as finishing.

**Cross-project data.** `storage/reviewAggregate.ts`'s `buildReviewAggregate(items, now)` is a pure, synchronous transform over the already-warm `dataCache.ts` cache — the exact same "no filesystem I/O, read what's already loaded" pattern `dailyAggregate.ts` established for Daily view (§2.3's "model for any future cross-project feature"). One aggregate covers steps 2, 4, 5, 6, 7, 8 in a single pass: `weekMeetings`, `stalledProjects`/`neglectedAreas` (each carrying its own next-2-meetings and shelved tasks), `doneProjects`, `onHoldItems`, `unfocusedNextItems` (each carrying its own open `#next` tasks via `nextTasksFor`). Step 1 (Overview) reads only `settings`, no aggregate. Inbox.txt (step 3) is loaded directly (`loadProjectFile('inbox', basePath)`), same as Daily view's own Inbox section, since it's outside the cache's per-item scan.

**Component reuse (explicit requirement for this feature).** Every "add a task" moment on this screen — the Week-ahead step's fixed-to-Inbox add, and each stalled-project/neglected-area card in the Stalled projects/Neglected areas steps — uses `ui/TaskQuickAdd.tsx`, the exact same component Daily view's own Tasks-column quick-add now uses (both extracted from what used to be `DailyView.tsx`'s own local, non-shared quick-add block). This is a deliberate, explicit deviation from §3's usual per-screen-presentation convention, called for by name during this feature's design ("creating meetings or todos should be same component here as on daily view"). `TaskQuickAdd`/`MeetingQuickAdd` originally wrapped `ui/DestinationPicker.tsx` for callers with no fixed destination; §2.20 made `fixedDestination` required on both everywhere, so neither renders a picker of its own any more — `DestinationPicker.tsx` itself survives only as `ui/GoogleCalendarPanel.tsx`'s own copy-destination picker (§2.17), unrelated to quick-add. Filing an Inbox item (the Inbox-to-zero step) is a different action — not task/meeting *creation* — and as of §2.20 it goes through the same `ui/FileBrowserPane.tsx` arming mechanism the Inbox tab and Project↔Area assignment (§2.19) use, not a bespoke picker; `ui/FileToPicker.tsx`, which used to serve this step (and, briefly, the Inbox tab — §2.16), is unused by any screen now.

**Resume behavior.** Which step you're on is kept in a module-level variable inside `ReviewScreen.tsx` (`savedStepIndex`), not plain React state — `App.tsx`'s tab switch genuinely unmounts the previous tab's screen (conditional rendering, no back-stack/`display:none`), so plain `useState` would reset to step 1 on every tab revisit. This is session-only (an app relaunch loses it, same as `dataCache.ts`'s own cache) and deliberately not persisted to settings; it resets to step 1 once "Finish review" completes, so the *next* visit starts a fresh cycle.

**The star badge.** `domain/settings.ts` gained `lastReviewCompletedAt: string | null` on `GtdParaSettings` and `isReviewOverdue(lastReviewCompletedAt, now)` (true if never completed, or the last completion was more than 7 days ago). `App.tsx` now loads `settings` into its own state (previously `reorient()` loaded settings only to resolve paths, never kept them) and passes `isReviewOverdue(...)` to `TabBar`'s new `reviewOverdue` prop, which renders a small "●" next to the Review tab's label. Deliberately passive — no active reminder/notification, exactly as scoped. `ReviewScreen`'s `onFinished` callback (called only by the Weekly focus reset step's "Finish review") lets `App.tsx` re-load settings immediately, so the badge clears without waiting for the next `reorient()`.

**Not yet verified on-device** (no on-device build access this session) — same standing caveat as §2.12's `moveFolder` addition. Worth a smoke test once on-device: run a full 9-step review against a real Projects/Areas tree — including the Overview step's recap rendering correctly after a "Finish review" and the new Unfocused next items step's per-task actions and "Add to Daily focus" — confirm Inbox filing actually moves (not duplicates) the line, and confirm the star badge clears after "Finish review" and reappears after 7 days (or by editing `lastReviewCompletedAt` directly in `AsyncStorage` for a faster check).

### 2.14 Flow-state tags (Next / Waiting For / Someday / Maybe)

An exclusive GTD flow-state per task, layered onto §2.10's existing general `#tag` mechanism rather than inventing a new syntax — full requirements/design history in `technical-design-tags.md` in this same `docs/` folder. Requirements were clarified in chat, then a Claude Design canvas sketch (create/view/edit across Daily and Project/Area Todos) was reviewed, then a technical design was written and locked in against the already-shipped Weekly Review flow (§2.13) before implementation.

**Data model.** `domain/types.ts`'s new `FlowState = 'next' | 'waiting-for' | 'someday' | 'maybe' | null` and two new `Task` fields, both derived from `text` on parse like every other Task field — never a second source of truth: `flowState: FlowState` and `waitingOn: string | null` (only meaningful when `flowState === 'waiting-for'`). `domain/flowState.ts` (new, zero RN imports, same domain-purity rule as `markdown.ts`) holds `deriveFlowState(tags)` (first match wins, in `next`/`waiting-for`/`someday`/`maybe` priority order — permissive about a hand-edited file carrying more than one flow tag, same "never load-bearing-fail on messy input" posture as every other parser here) and `deriveWaitingOn(tags)` (the slug out of a `#waiting-for:<slug>` tag). `domain/markdown.ts`'s `deriveTaskFields` now returns `flowState`/`waitingOn` alongside `tags`/`dueDate`.

**Waiting-on encoding.** `#waiting-for:<slug>` — mirrors the existing `#due:YYYY-MM-DD` tag shape exactly rather than inventing new syntax. `slugifyWaitingOn(input)` turns free text typed into a "Waiting on" field into a tag-safe slug (lowercase, non-`[a-z0-9-]` runs collapsed to one `-`, trimmed) — deliberately lossy, same accepted trade-off `#due:` already lives inside. `titleCaseSlug(slug)` reverses it for display (`meier-sohn` → `Meier Sohn`) in badges.

**Mutation.** `domain/flowState.ts`'s `setFlowStateTag(text, next, waitingOnSlug?)` is the one place UI code edits `text` for flow-state: strips any existing flow-state tag (bare or `waiting-for:<slug>`) and appends the new one, if any. `markdown.ts`'s new `setDueTag(text, dueDate)` does the equivalent for the due-date tag. Every create/edit surface composes both before handing the caller a plain string; callers immediately re-derive `tags`/`dueDate`/`flowState`/`waitingOn` via `deriveTaskFields`, same "text is truth, tags are a derived read of it" rule as everywhere else in this codebase.

**Daily and flow states.** `storage/dailyAggregate.ts`'s `buildDailyAggregate` keeps Someday/Maybe tasks off Daily. Waiting For tasks have their own rule (`domain/flowState.ts`'s `isWaitingForShownOnDaily`): every open Waiting For task from any Project, Area or the Inbox shows when it has no due date or its date is today or earlier, focused or not; a future date keeps it off Daily until that day (the date works as the follow-up date). `groupDailyTasksByItem` sorts Waiting For tasks last inside their group. The `#next` check reads `task.flowState === 'next'`. Focus mode's own builders (`buildNowEntries`, `buildFocusCandidateEntries`) don't use this rule, so Waiting For tasks never appear there.

**Weekly Review interaction.** See §2.13's own updated writeup — `storage/reviewAggregate.ts`'s stalled/neglected check now discounts Someday/Maybe tasks (`isActionableOpenTask`), and surfaces them per-item as `shelvedTasks` with a promote-to-Next action, rather than either counting them as open work or silently hiding them.

**Grouping (Project/Area Todos).** `domain/flowState.ts`'s `groupTasksByFlowState(tasks)` buckets a project's own not-cancelled tasks into Next / Waiting For / Someday / Maybe / Other, in that fixed order, empty groups omitted — same "omit empty groups" convention §2.12's status sections already established. `screens/ProjectDataPanel.tsx`'s `TodosSection` renders these groups with a subheading each, replacing the old flat list.

**Shared UI components, reused rather than duplicated per screen** (this feature's other explicit requirement, alongside locking in against Weekly Review): `ui/FlowStateChips.tsx` (the Next/Waiting For/Someday/Maybe pill row — visually identical to `ProjectDataPanel`'s existing status-picker pills, reused rather than reinvented; unlike a status picker, a chip can be un-selected back to `null`), the todo labels (§2.15: `domain/taskLabels.ts` + `ui/TaskLabels.tsx` — flow state in flat lists only, since the label is the only way it reads as such there; Waiting-on and Due/Overdue everywhere), and `ui/TaskEditCard.tsx` (a bordered edit card — text, chips, conditional Waiting-on field, Due field, Save — replacing the old bare single-line edit `TextInput` on every task-row surface). `ui/TaskQuickAdd.tsx` gained the same chips/due/waiting-on fields inline, composing tags into its already-opaque `text` param before calling `onAdd` — every existing caller (Daily's quick-add, Weekly Review's look-ahead and per-card quick-adds) gained tag support with zero changes on their end, since none of them read or interpret that string. One layout deviation from the reviewed sketch: `TaskQuickAdd`'s due-date field sits stacked below the chip row rather than beside it (an `marginLeft: 'auto'` same-row layout was judged too risky to ship unverified with no on-device build access this session) — functionally identical, a few pixels taller.

**Wired into:** `screens/ProjectDataPanel.tsx`'s `TodosSection` (grouping, shared add/edit), `screens/DailyView.tsx`'s Open-tasks rows and Inbox rows (badges; edit rows now use `TaskEditCard`), `screens/ReviewScreen.tsx` (badges on Inbox-to-zero cards; shelved-task promotion on Stalled/Neglected cards, per §2.13).

**Not yet verified on-device** (no `device_bash`/on-device build access this session, same standing caveat as §2.12/§2.13's native and cross-project additions) — no `tsc --noEmit` or `eslint` pass could be run against this feature's files. Worth running the project's usual scratch-project `tsc --noEmit` + `eslint` pass, and the standalone-Node verification convention (§3) for `deriveFlowState`/`deriveWaitingOn`/`slugifyWaitingOn`/`setFlowStateTag`/`groupTasksByFlowState`, before relying on this in daily use.

**`screens/InboxScreen.tsx`** (new). The "hide done tasks" toggle (§2.15) moved here from Daily view, still backed by the same `hideDoneInboxTasks` setting.

**Grouping index-safety fix (found during this pass).** While writing `InboxScreen.tsx`'s flow-state grouping, a real bug was found in the existing `ProjectDataPanel.tsx`'s `TodosSection`: it filtered `tasks` by `hideDone` *before* calling `domain/flowState.ts`'s `groupTasksByFlowState`, which computes each returned entry's `index` relative to whatever array it's given. Every row-mutation handler (`commitEdit`, `handleToggleDone`, `handleCancel`, …) does `tasks.slice(); next[index] = ...` against the *full*, unfiltered `tasks` array — so with "Hide done tasks" active and an earlier task in the full array happening to be done (and thus filtered out before grouping), editing or toggling a later *visible* task would silently mutate the wrong task instead, due to the index misalignment between the filtered array `groupTasksByFlowState` saw and the full array every handler actually indexes into. This was a genuine, demonstrable data-corruption risk, not a style nit — self-discovered via code review, not user-reported. Fixed in `ProjectDataPanel.tsx` by grouping against the full `tasks` array first, then filtering each group's already-indexed `entries` afterward when `hideDone` is on (preserving every surviving entry's correct `index`); `InboxScreen.tsx`'s own grouping was written with this same safe order from the start, to avoid reintroducing it. The same map-then-filter-not-filter-then-map reasoning applies to meeting-list index capture (`splitAndSortMeetings`-style splitting) wherever it appears.

**Daily aggregate widened.** `storage/dailyAggregate.ts`'s `DailyItemRef.kind` widens from `'project' | 'area'` to the full `GtdParaKind`, and a new synthetic `inboxItemRef(basePath)` gives Inbox-sourced entries a `DailyItemRef` shaped just like any Project/Area's — this is what lets Daily view's Calendar/Open-tasks columns treat an Inbox-sourced row exactly like any other source (§2.11), rather than needing a parallel Inbox-specific code path. `App.tsx`'s new `openInbox` handler (switches to the Inbox tab) is what a Daily-view row's "jump to source" affordance calls for an Inbox-sourced entry, in place of `onOpenItem` (there's no Project/Area folder to open for those).

**Tab registration.** `ui/TabBar.tsx`'s `AppTab` type and `TABS` array both gain `'inbox'`, placed right after `'daily'` — both are "flow" tabs (where captured/triaged work lands and gets acted on day-to-day), ahead of the more structural Current/Review/Settings tabs. `App.tsx` renders `InboxScreen` in its own tab branch, registered with the shared refresh icon (§2.15) the same way every other tab is.

**Not yet verified on-device** (no `device_bash`/on-device build access this session, same standing caveat as every feature above) — no `tsc --noEmit` or `eslint` pass could be run against this feature's files; only a standalone TypeScript-compiler-API syntax check (parse-only, no type information) and manual prop-shape cross-referencing against every caller were possible this session. Worth a dedicated on-device pass once built: exercise the Inbox tab's full task/meeting CRUD, confirm Daily view's Inbox-sourced rows edit/cancel/note-link correctly (including the "jump to Inbox tab" affordance), and specifically re-verify the "Hide done tasks" toggle in both `ProjectDataPanel`'s Todos section and the new Inbox tab against the index-safety fix above — a regression there would silently corrupt the wrong task's edit, not throw.

### 2.17 Google Calendar (ICS link) integration

Read-only sync of a Google Calendar (or any ICS-publishing calendar) into upcoming-meeting suggestions, requested and clarified across several rounds of chat before any code: what to fetch and where to show it, then the network-permission model, then a UI-alignment correction (Daily view's own layout as the template for every other surface), then Settings restructuring — each round's answers folded into the next before `docs/dev/technical-design-google-calendar.md` was written up and implementation began. Feasibility was verified not with an on-device spike but by inspecting the sibling `SNFolio` project on the local drive, which already ships a working `ensureInternetPermission` call and a complete zero-dependency ICS/RRULE parser — both ported/trimmed into this project rather than re-derived or pulled in as a new dependency (`ical.js` was the fallback plan, never needed). Full requirements/design history and the build order followed: `docs/dev/technical-design-google-calendar.md`.

**Data model and settings.** `domain/googleCalendarEvent.ts`'s `GoogleCalendarEvent {uid, title, date, time, allDay}` — deliberately not a `Meeting`; nothing links a Google event back to its source once copied (§ "Copy action" below). `GtdParaSettings` (`domain/settings.ts`) gains `googleCalendarIcsUrl: string`, plaintext in the same `AsyncStorage` JSON blob as every other plugin-config field (§2.7) — a bearer credential stored the same way this app already stores everything else non-content, flagged in its own doc comment rather than silently accepted.

**Permission.** `supernote/pluginPermissions.ts`'s new `ensureInternetPermission()` wraps `plugin.permission.INTERNET` through the same `ensurePluginPermission`/8-second-timeout machinery `ensureFileReadPermission`/`ensureFileWritePermission` already use (§2.8) — found in `sn-plugin-lib`'s own `PluginManager.ts` source and confirmed live in `SNFolio`. Requested lazily, only on the first actual fetch attempt (never on plugin launch or Settings mount), so a user who never links a calendar is never prompted.

**Bug found post-implementation: the runtime call alone isn't enough.** `ensureInternetPermission()` shipped correctly, but the permission was never actually declared in `PluginConfig.json`'s `uses-permissions` array — the plugin-manifest-level declaration (this SDK's own equivalent of an Android `<uses-permission>` entry) that has to list a permission before the host will let the runtime `hasPermission`/`requestPermission` calls do anything with it, same as `FILE:READ`/`FILE:WRITE` are already declared there for the file permissions (§2.8). This was missed originally because feasibility was verified against `SNFolio`'s `pluginPermissions.ts`/`AgendaScreen.tsx` (the runtime call site) without also cross-checking its `PluginConfig.json`, which does list `plugin.permission.INTERNET` alongside its file permissions. Symptom on-device matched exactly: no permission prompt at all, only the file read/write ones from unrelated operations. Fixed by adding `"plugin.permission.INTERNET"` to `PluginConfig.json`'s `uses-permissions` array. Like any other `PluginConfig.json` change, this needs a rebuild and reinstall (not just a JS reload) to take effect on-device.

**ICS parsing.** `domain/icsParser.ts` — line unfolding, `VALUE=DATE` all-day events, `TZID` conversion via `Intl.DateTimeFormat` (no bundled tz database), RRULE expansion (`DAILY`/`WEEKLY`/`MONTHLY`/`YEARLY` with `BYDAY`/`BYMONTHDAY`/`INTERVAL`/`COUNT`/`UNTIL`), `EXDATE`, and `RECURRENCE-ID` override folding — ported from `SNFolio`'s own parser, trimmed to VEVENT-only (drops VTODO/attendees/description, none of which this feature surfaces) and re-shaped around a single `expandEventsForRange(events, start, end)` pass rather than `SNFolio`'s per-day expansion. Verified with a standalone Node script (`TS_NODE_COMPILER_OPTIONS`-based, same throwaway-script convention as `verify-markdown.ts`/`verify-aggregate.ts`, §3) covering unfolding, all-day/UTC parsing, cancelled-event filtering, weekly RRULE + `EXDATE`, and a `RECURRENCE-ID` override — all passing before the module was wired into the app.

**Fetch and cache.** `storage/googleCalendarCache.ts` holds one module-level `GoogleCalendarCacheState {fetchedAt, events, error?}` shared by every mounted `GoogleCalendarPanel` instance across Daily/Current/Inbox/Review — a single today-through-+30-days fetch per session (or manual Refresh), never one fetch per surface. `refreshGoogleCalendar(icsUrl)` calls `ensureInternetPermission()` first, enforces https (`webcal://` upgraded, plain `http://` rejected), and never throws past itself — a fetch failure sets `state.error` for the panel to render inline rather than crashing the surface it's embedded in.

**Dedup.** Title+date+time string matching against every cached Project/Area's meetings plus Inbox's own (`alreadyCopiedKeys`) — an explicit, deliberately simpler choice over a more robust ICS-UID-based scheme that would have meant a `Meeting` schema change; a matched Google event renders with a ✓ and can't be copied again.

**Copy action.** `storage/googleCalendarCopy.ts`'s `copyGoogleEventToDestination(event, destination, basePath)` builds a plain one-off `Meeting` (title/date/time only — copying one occurrence of a recurring Google event takes just that occurrence's own start date/time, since gtdpara has no recurring meetings) and runs it through the same `saveMeetings`-then-cache-write-through pair (file first) every other Meeting mutation in this codebase uses (§3) — indistinguishable from a hand-added meeting from that point on, nothing links it back to the source event.

**Shared UI.** Two new `ui/` components, used identically everywhere rather than four bespoke surfaces:

- `ui/MiniTabs.tsx` — a small generic segmented switcher (label row, active underline, no icons/counts), used both 2-way (existing view | Google) in every calendar-showing surface and 3-way (Folders | Focus | Calendar) in Settings.
- `ui/GoogleCalendarPanel.tsx` — the actual Google-tab content: a Refresh link, the day-window-filtered event list (checkmarked where already copied), and an inline expandable `DestinationPicker` (reused as-is, §2.11/§2.12) + Copy button per event. Takes `maxDays` to narrow the shared 30-day cache for *display* only (the fetch window itself never changes per caller) and a `defaultDestination` so each surface's Copy defaults sensibly (Inbox for Daily/Inbox/Review, the current item for Project/Area). An empty `icsUrl` renders a "No Google Calendar linked yet" state linking to Settings' Calendar tab (`onOpenSettings`) instead of the list.

**Integration points**, each wrapping its existing meetings content as one `MiniTabs` tab and `GoogleCalendarPanel` as the other:

- `DailyView.tsx` — Calendar column, `maxDays={2}` (matching its existing Today/Tomorrow window), default destination Inbox.
- `ProjectDataPanel.tsx` — `MeetingsSection`, `maxDays={30}` (the full fetch window, no shorter display cap here), default destination the current Project/Area.
- `InboxScreen.tsx` — left pane, `maxDays={30}`, default destination Inbox.
- `ReviewScreen.tsx`'s Week-ahead step — `maxDays={7}` (matching that step's own 7-day look-ahead), default destination Inbox.

`App.tsx`'s new `openSettingsCalendar` handler (threaded to all four surfaces above, and through `ItemDetail.tsx` down to `ProjectDataPanel`) sets a `settingsTab` piece of state to `'calendar'` before switching to the Settings tab, so a panel's empty-state link lands directly on the right sub-tab rather than just Settings in general; a direct `TabBar` tap on Settings resets it back to `'folders'` first, so the jump-target doesn't linger past the visit it was meant for.

**Settings restructuring.** `Settings.tsx`'s previously single scrolling body — folder-path fields, then a "Focus slots" heading, then those four counts — is now three `MiniTabs` sub-tabs (Folders/Focus/Calendar) so each is reachable with no scrolling, per an explicit correction during chat clarification. Folders and Focus are unchanged content, just tab-gated; Calendar is new (the ICS-URL field plus a "Paste from clipboard" button, `@react-native-clipboard/clipboard` — this project's first third-party native module besides its own `GtdParaFileModule.kt`, so it needs `npm install` **and** a native Android rebuild, not just a JS reload, before it'll work on-device). Save stays one shared action across all three tabs (simplest — avoids three separate save states); `clearCachedData()` on save stays scoped to the folder-path fields exactly as before, since a URL change doesn't touch `dataCache.ts`.

**Known open assumptions** (carried from chat clarification, stated rather than blocking): a multi-day all-day Google event displays on its start date only; `DestinationPicker`'s existing Active-only/focused-first filtering (§2.12) applies unchanged to the copy target, with no Google-specific carve-out.

**Not yet verified on-device**, same standing caveat as §2.16 and every feature before it (no `device_bash`/on-device build access this session): no `tsc --noEmit`/`eslint` pass, no actual `npm install` for the new clipboard dependency, no native Android rebuild, and no real ICS URL has been fetched against a live Google Calendar. Only the ICS-parser's own standalone-script verification, a TypeScript-compiler-API syntax check per touched file, and manual prop-shape cross-referencing against every caller were possible this session. Worth a dedicated on-device pass once built: `npm install` + rebuild for the clipboard dependency, link a real ICS URL and confirm the permission prompt appears exactly once (on first sync, not on Settings mount), confirm the 30-day fetch against the today/2/7/30-day per-surface display windows, and confirm dedup checkmarks agree across all four surfaces after copying an event from any one of them.

### 2.18 Linked files (Todos & Meetings)

Lets a Todo or Meeting point at **one** existing file — not a note this plugin creates (that's §2.4's separate, unchanged linked-*notes* mechanism), but an arbitrary existing file the user already has under Projects/Areas or Resources (a screenshot, a PDF export, a template). Requirements were clarified in chat across three UX rounds (row icon, arming/picking flow, per-item default Resources folder, the Inbox restructure that falls out of it), then written up as `docs/dev/technical-design-linked-files.md` before implementation, per this project's standing workflow. Full requirements/design history in that same `docs/` folder.

**Data model.** `domain/types.ts`'s `Task`/`Meeting` both gain `linkedFile: string` (base-root-relative, e.g. `"1 Projects/Squad Value/Sprints/Sprint_Board_Export.png"`; `''` = no link) — deliberately base-relative rather than item-relative like `notePath`, since a linked file can live under Resources, which isn't nested under the item's own folder. Storage is a new trailing `+[[path]]` token, appended **after** the existing `→ [[path]]` note-link token (`domain/markdown.ts`'s `LINKED_FILE_RE`/`extractLinkedFile`/`appendLinkedFile`); parse order strips right-to-left (`extractLinkedFile` before `extractNoteLink`, both before `deriveTaskFields`), serialize order appends left-to-right, so round-tripping reproduces the exact token order. `defaultResourceFolder: string | null` is a new frontmatter field (relative to `paths.resources`) — parsed/written the same "omit when null" convention `dailyFocus`/`weeklyFocus` already use, threaded through `saveFrontMatter`/`CachedItem` the same way those two were.

**Storage.** New `storage/linkedFiles.ts`, parallel to `storage/noteLinks.ts` but for pointing at an existing file rather than creating one: `resolveLinkedFilePath`/`toLinkedFile` (base-relative ⇄ absolute), `linkedFileStatus` (async — 'ok'/'missing', by listing the file's parent folder and checking for a matching name), and `locateLinkedFile(paths, itemPath, linkedFile)` (which root — item vs. Resources — and the containing folder's path, for the Files pane's auto-navigate). Inbox has no item root of its own, so `InboxScreen.tsx` passes `paths.resources` as both the itemPath argument and the implicit resources root — `locateLinkedFile`'s two internal checks then resolve identically, which is correct since every Inbox link necessarily lives under Resources.

**`ui/FileBrowserPane.tsx`** (new) — `ItemDetail.tsx`'s left-pane file browser, extracted once Inbox's rebuilt left pane needed the identical shape (folder-stack navigation, pagination, now locating/arming/pin) — the same "extract once a second caller needs the same shape" bar `TaskRow`/`FileToPicker` were built to. Three modes via a `LinkTarget` discriminated union: normal (today's drill-in/open-file behavior, unchanged), `locating` (auto-navigates to a linked file's folder and pages to it — `ui/pagination.ts`'s new `pageIndexOf`/`jumpTo` addition, purely additive alongside the existing `resetKey` — highlighting the matching row with a solid black 4px left border, the one deliberate departure from `#2f6feb` across this whole feature, since blue doesn't hold up on e-ink), and `arming` (a "Select Attachment ✕" affordance sits inline; tapping a *file*, not a folder, completes the link instead of opening it). The Resources root alone supports a per-item default-subfolder pin — an outline pin icon in the breadcrumb row, filled and non-tappable once the browsed subfolder matches the pinned one.

**"Up" navigation fix (2026-09-07, user-reported).** The pane's pinned-default and `locating`-mode navigation both originally collapsed the folder stack to a single level, which hid the "‹ Up" affordance even when the current folder wasn't the browsing root — meaning there was no way to navigate above a pinned default, or above wherever `locating` had auto-navigated to, to pick a *different* folder as the new default. Fixed with a `buildStack(root, relativePath)` helper that builds the full stack from the root down to the destination (one level per path segment) instead of collapsing to one; "Up" is now available at every level except the root itself, exactly matching "keep Up unless the selected default is Resources itself."

**Row changes.** `ui/TaskRow.tsx`/`ui/MeetingRow.tsx` lose `onCancel`/the `✕` render branch entirely — soft-delete moved into edit mode (below). New `linkedFile`/`onOpenLinkedFile`/`onArmLink`/`isArming` props drive a clip-icon cluster in the same slot: a filled clip (tap → open) when `linkedFile` is set, always rendered regardless of whether `onArmLink` was passed (this is what makes Daily's/Review's clip read-only — see below); a `+`-prefixed clip (tap → arm) when empty and `onArmLink` is provided; nothing when empty and no `onArmLink`. New `ui/icons.tsx` draws the clip and pin glyphs as small black-stroke `react-native-svg` shapes (paths lifted directly from the approved mockup) rather than emoji, per explicit e-ink-legibility feedback during the UX rounds — `react-native-svg` (`^15.11.2`) is a genuinely new `package.json` dependency, not something already resolved transitively, so it needs an actual `npm install` on-device before this builds (see the verification note below).

**Edit-form changes.** `ui/TaskQuickAdd.tsx`/`ui/MeetingQuickAdd.tsx` gain a "Delete" button next to "Save" in edit mode (`onDeleteEdit`, the same soft-delete mutation the retired row `✕` used to trigger) and a `linkedFileMissing` prop (caller-computed via `linkedFileStatus`, keeping the forms themselves free of I/O) that renders a ⚠ next to the attachment pill. The attachment itself needs no new save-time callback: `editingTask?.linkedFile`/`editingMeeting?.linkedFile` seeds local state the same way `flowState`/`dueDate` already are, rendered inline as a clip(+⚠)+✕ pill when non-empty (only the ✕ is interactive here, clearing local state); `submit()` composes the final text via a new `setLinkedFileTag`, mirroring `setDueTag`'s shape. This makes "swap" a two-trip flow by design — clearing here and saving writes `linkedFile: ''` immediately, and a *new* link is only ever set by arming from the row afterward, never from inside the edit form itself.

**Cross-cutting: one edit target.** `ProjectDataPanel.tsx`'s `TodosSection`/`MeetingsSection` used to each own an independent `editingIndex` (a task edit and a meeting edit could be open simultaneously); this moves up into `ProjectDataPanel` itself as a shared `EditTarget = {type: 'task'|'meeting'; index: number}` plus a parallel `armTarget` of the same shape — starting an edit or an arm on either row type now clears whichever of the other three states was active, so exactly one edit-or-arm target exists per screen at a time, which is also what keeps the Files pane's auto-locate unambiguous. `ProjectDataPanel` derives the `LinkTarget` (`locating` when editing an item with a non-empty `linkedFile`, `arming` when arming, `null` otherwise) and reports it up via a new `onLinkTargetChange` prop; `ItemDetail.tsx` stores whatever was last reported and passes it straight into `FileBrowserPane`. `InboxScreen.tsx` (below) gets the identical `editTarget`/`armTarget` merge, just without a second screen-level component to bubble through.

**`InboxScreen.tsx` rebuild.** Previously a Meetings-left/Tasks-right two-pane layout; now mirrors `ItemDetail.tsx`'s shape more directly — left pane is `FileBrowserPane` with a single `resources` root (no Project Files tab, no `MiniTabs` — Inbox items aren't filed anywhere yet, so there's no "item" root to offer), right pane stacks a Tasks section above a Meetings section (each with its own quick-add, and Meetings keeping its existing Meetings/Google `MiniTabs`) rather than the old side-by-side columns — new `PAGE_SIZE.inboxTasks`/`inboxMeetings` constants (5/3, starting at the same values as `projectTodos`/`projectMeetings` pending on-device tuning, per that pair's own "don't silently retune one by touching the other" rule) replace the old shared `column` size. Tapping a row's clip when nothing's armed opens `linkTarget: 'arming'` against this single Resources root exactly as `ProjectDataPanel`'s does against its Resources root. **Widened by §2.20**: the "Inbox items aren't filed anywhere yet" framing above is now out of date — filing is exactly what this tab is for. The left pane's roots grew from just Resources to Resources/Projects/Areas, and each row's File action arms that same pane restricted to just the Projects/Areas tabs (`pickKind: 'folder'`), alongside the pre-existing Link arming against all three.

**Daily: read-only; Review: gained Link (§2.20).** `DailyView.tsx`'s Open-tasks/Calendar rows pass `linkedFile`/`onOpenLinkedFile` into the shared `TaskRow`/`MeetingRow` calls but omit `onArmLink` — a filled clip opens the file, an empty one renders nothing, and there's no way to start a link from Daily view, since it has no Files pane to auto-locate against. Review's Inbox-to-zero step was originally defaulted to this same read-only treatment too (an explicit, flagged assumption in this feature's technical design, since at the time neither screen had a Files pane), but that assumption didn't survive contact with §2.20's filing-unification pass: that step now has its own Files pane (the same one File arms), so it gained `onArmLink` alongside `onArmFile` — see §2.20.

**A recurring bug pattern, found and fixed in three places during this pass.** Several edit-cancel/edit-commit handlers closed edit mode unconditionally by chaining `.then(() => close())` after an action-runner (`runTaskAction`/`runMeetingAction`) that swallows its own errors internally — so a failed save would still close the form as if it had succeeded, silently discarding the edit. Fixed in `ProjectDataPanel.tsx`'s `MeetingsSection.commitEdit`, `ReviewScreen.tsx`'s `handleInboxTaskCancel`/`handleInboxMeetingCancel`, and `DailyView.tsx`'s `commitTaskEdit`/`commitMeetingEdit`/`handleCancelTask`/`handleCancelMeeting` — in every case by moving the "close edit mode" call inside the async try block, immediately after the successful save, rather than chaining it onto the outside. Worth keeping in mind for any future edit-form handler: close on confirmed success, never on "the call finished."

**Verified** via a full `tsc --noEmit --strict` sweep (the project's scratch-shim convention, §3) across every file this feature touched, run repeatedly through the implementation and once more as a final pass — clean, zero real errors (the only output is the same pre-existing module-resolution/implicit-any noise from files outside this session's working subset, confirmed by diffing against each file's untouched original). **Not yet verified on-device** (no `device_bash`/on-device build access this session, same standing caveat as every feature since §2.12): no `eslint` pass (no config staged this session either), no actual `npm install` for the new `react-native-svg` dependency, and no on-device smoke test. The Phase-4 checkpoint (linking a file from each root on the Current tab, opening a linked file, the pinned-default-folder flow, and the "Up" navigation fix above) was exercised and confirmed by the user mid-implementation; still open for an on-device pass: Inbox's Resources-only linking, Daily/Review's read-only clips, remove+relink via the edit form's ✕, Delete from edit mode, and the missing-file ⚠ path (rename a linked file's on-disk target, reopen edit).

### 2.19 Project↔Area assignment, Area Files

Lets a Project optionally support **one** Area — a lightweight relationship, not a hierarchy (Projects still live flat under `1 Projects/`, Areas flat under `2 Areas/`; assignment is a frontmatter reference, not a folder move). Requirements were clarified in chat across two rounds, then written up as `docs/dev/technical-design-project-area-assignment.md` (plus a Claude Design canvas covering the unassigned/assigned Project view, the Areas tab armed for picking, an Area's own Current tab, and the two Archive dialogs) before implementation, per this project's standing workflow.

**Data model.** `domain/types.ts`/`domain/markdown.ts`'s `ParsedFrontMatter`/`FrontMatter` gain `area: string | null` — the assigned Area's bare folder name (same identity convention every other Project/Area reference in this codebase uses — no synthetic IDs), or `null`. Same "omit when null" convention `defaultResourceFolder`/the focus flags already use: a new `AREA_LINE_RE`/`area:` line in `parseFrontMatter`, written only when set in `writeFrontMatterIntoContent`. Always `null` for Areas — the parser stays permissive about what it *reads* regardless of kind (same posture as `status`), but nothing in the UI ever writes it for one. Threaded through `saveFrontMatter`/`ProjectFileState`/`CachedItem`/`updateItemFrontMatter` as a new trailing parameter, defaulting to `null` — see the correctness note below on why every *existing* frontmatter-writing call site needed an explicit audit, not just the new ones.

**Storage.** New `storage/areaAssignment.ts`: `assignProjectToArea(project, areaName)`/`unassignProject(project)` (plain frontmatter writes, no side effects on the Area itself) and `assignedProjects(areaName)` (every cached Project currently pointing at `areaName`, read from the already-warm cache — the one place this whole feature's "which Projects does this Area support" question gets answered, reused by every lifecycle rule below rather than re-filtered ad hoc).

*Lifecycle coupling*, matching the user's explicit rules:
- **Area → On Hold cascades** to every currently-Active assigned Project, via a recursive `setItemStatus` call inside `storage/statusControl.ts` — each cascaded Project's own focus-flag auto-clear fires too, unchanged. Deliberately **not** symmetric: Area On Hold → Active never reactivates those Projects, the same one-directional posture the focus-flag auto-clear already has.
- **Archiving an Area is blocked** (`storage/archive.ts`'s `describeAreaArchiveBlock`, factored out specifically so `ui/ItemStatusPanel.tsx` can run it *before* even opening the destructive "Move to Archive?" confirmation) if any assigned Project is still Active or On Hold — the message names them. Otherwise, every assigned Project that's Done is cascaded into `archiveItem` first, before the Area's own folder moves; a cascaded archive's failure stops the whole operation rather than completing over a partial cascade.
- **No code needed for "archived Areas keep a valid reference."** Assignment is stored by bare folder name, and archiving an Area only moves its parent folder (never renames it) — so a cascaded-or-already-Done Project's `area` field is left untouched and stays correct after the move, by construction. Flagged during design as a place where the obvious-sounding requirement ("archiving should update all projects to point to archived area") turned out to need *no* implementation at all once the identity model was traced through.

**UI.**

- `ui/ItemStatusPanel.tsx` — a new "Assign to Area…" button sits in the same row as "🗄 Archive…", Projects only; once assigned it becomes an "Area: `<name>` ✕" pill (tap the name to re-arm and reassign, tap ✕ to clear immediately — reversible, no confirmation, unlike Archive). Picking works exactly like linked-files arming: this component doesn't own a file browser of its own, so pressing the button reports a `LinkTarget` up via a new `onRequestAreaAssignment` prop — the same shape `ProjectDataPanel`'s existing `onLinkTargetChange` already uses, just from a different UI element (§2.18's `LinkTarget` union, reused rather than duplicated). `handleArchivePress` runs `describeAreaArchiveBlock` synchronously before opening the confirmation dialog for an Area, so the destructive dialog is never even offered when archiving isn't actually allowed yet.
- `ui/FileBrowserPane.tsx`'s `FileBrowserRoot` gains `entryFilter?: (entry) => boolean` — applied only at a root's own top level (depth 0; a folder entered from there shows its real, unfiltered contents), used by a Project's new "Areas" tab (Active-status areas only, cross-referencing the cache) and an Area's new "Project Files" tab (Projects assigned to it, via `assignedProjects`). `LinkTarget`'s `arming` variant gains `pickKind?: 'folder'` (a top-level folder tap picks immediately instead of drilling in — how "Assign to Area…" picks an Area itself, as opposed to a *file inside* one), `label?: string` (overrides the "Select Attachment" badge text — "Select Area" here), and `root?: string` (auto-switches to and resets that root when arming starts, so "Assign to Area…" always begins the pick at the Areas root regardless of which tab was last open). All three are additive — omitted, they reproduce §2.18's file-linking arm exactly.
- `screens/ItemDetail.tsx` — file-browser roots are now kind-dependent: a Project gets Project Files / Resources / Areas (the last entry-filtered to Active, armed with `root: 'areas'` for the assignment pick) plus a fourth **Area Files** tab once one is assigned (pointed straight at that Area's own folder); an Area gets its own folder (relabeled **Area Files**) / Resources / **Project Files** (entry-filtered to its assigned Projects). Two separate `LinkTarget` states (`dataPanelLinkTarget`, from `ProjectDataPanel`'s existing report; `areaLinkTarget`, from `ItemStatusPanel`'s new one) are merged as `areaLinkTarget ?? dataPanelLinkTarget` rather than sharing one setter — `ProjectDataPanel`'s own reporting effect re-fires with `null` on changes unrelated to area-assignment, which would otherwise risk clobbering an in-progress area-assignment arm out from under it. Accepted trade-off, documented inline: canceling an area-assignment arm while a file-link edit/arm was already active elsewhere reveals that other state as-is (it's never told to cancel), rather than restoring some prior "nothing armed" state — a rare interaction, not worth building full bidirectional cancellation between the two components for.
- `storage/linkedFiles.ts`'s `locateLinkedFile` gains an optional third root check (`areaFolderPath`) — a Project's own assigned Area's folder, alongside its own item folder and Resources — so a Todo/Meeting already linked to a file under the assigned Area's Files tab still auto-locates correctly when the row is reopened for editing. (The reverse direction — an Area's own Todo linking to a file under one of *its* assigned Projects' folders via the new Project Files tab — isn't covered by any of the three known roots; picking such a file still links it, it just won't auto-locate on re-edit, same "returns null" fallback `locateLinkedFile` already has for anything unexpected.)

**A correctness gap found and fixed while implementing this feature, not part of its own scope.** `storage/focusSlots.ts`'s `setItemFocus` (toggling a Focus checkbox) called `saveFrontMatter`/`updateItemFrontMatter` without an `area` argument at all — since both default that parameter to `null` when omitted, turning a Focus checkbox on or off would have silently *cleared* a Project's Area assignment on every single toggle. Found by auditing every existing `saveFrontMatter`/`updateItemFrontMatter` call site once `area` became a real parameter on both (not just the ones this feature added), the same discipline §2.12's "extend, don't duplicate" frontmatter pattern calls for whenever a shared function's parameter list grows. Fixed by widening `setItemFocus`'s own `Pick<CachedItem, ...>` to include `area` and threading it through unchanged, exactly like `dailyFocus`/`weeklyFocus`'s own already-correct pass-through. `screens/ItemDetail.tsx`'s Resources-root pin (`handleSetDefaultResourceFolder`) had the identical gap and was fixed the same way. Also found and fixed in passing: `domain/types.ts`'s `Task`/`Meeting` interfaces were missing the `linkedFile: string` field entirely despite it being read/written throughout `markdown.ts`/`dataCache.ts` since §2.18 — a gap from that feature's own implementation, invisible until something else forced a fresh look at those two interfaces.

**Verified** via a syntax-only TypeScript-compiler-API parse check (no `node_modules`/RN types staged this session, so not a real `tsc --noEmit`) across every file this feature touched — clean, no parse errors — plus a manual argument-order/field-completeness audit of every `saveFrontMatter`/`updateItemFrontMatter`/`setItemStatus`/`archiveItem`/`setItemFocus`/`assignProjectToArea`/`unassignProject` call site (the class of bug the paragraph above already found one instance of), and a throwaway Node script (esbuild-bundled `domain/markdown.ts`, run directly — this project's standard standalone-script convention, §3) covering the new `area` frontmatter field: parse/omit-when-null/round-trip alongside `defaultResourceFolder`, extra-line preservation, and clearing the line back out on unassignment — all 8 checks passing. **Not yet verified on-device** (no `device_bash`/on-device build access this session, same standing caveat as every feature since §2.12): no real `tsc --noEmit --strict` or `eslint` pass against the actual project config, and no smoke test of the Archive block/cascade dialogs, the On-Hold cascade, or the four-root Files pane against a real Projects/Areas tree.

### 2.20 Filing unification (arm-based Files pane everywhere, retired destination pickers)

Generalized the "arm a `FileBrowserPane` tab, browse, tap to pick" mechanism §2.19 built for Project↔Area assignment across every remaining place the app used to show a bespoke destination/filing picker, and used the pass to close out a related loose end (a Lasso capture reset bug) found along the way. Clarified in chat — including two explicit multiple-choice decisions — then written up as `docs/dev/technical-design-filing-unification.md` before implementation, per this project's standing workflow. Full requirements/design history in that same `docs/` folder.

**The core reuse.** `ui/FileBrowserPane.tsx`'s `roots`/`entryFilter`/`LinkTarget` machinery (§2.18/§2.19) needed **zero code changes** to cover filing — `pickKind: 'folder'` (a depth-0-only pick, built for "Assign to Area…") is exactly the mechanism a "pick a Project/Area to file this into" action needs too. `storage/inboxFiling.ts` gains `resolveFilingPick(paths, root, relativePath): InboxFilingTarget | null`, the shared root→target mapping both filing screens need (previously each would have duplicated it); `fileInboxTask`/`fileInboxMeeting` themselves are unchanged.

**Every quick-add now goes straight to Inbox — no picker.** `ui/TaskQuickAdd.tsx`/`ui/MeetingQuickAdd.tsx`'s `fixedDestination` prop changed from optional to **required**, removing the "no `fixedDestination` = show a picker" mode entirely — `items`/`initialDestination` props and the internal `destination`/`pickerOpen` state are gone. This was one of the two explicit multiple-choice decisions made during clarification ("Always Inbox" over letting a Daily/Review-step quick-add target any Project/Area) — chosen for both Daily view's Calendar/Open-tasks quick-adds and Review's Week-ahead step quick-add. Every existing caller already either had a real fixed destination (`ProjectDataPanel`'s Todos/Meetings sections, `{type: 'item', ...}`) or gets a new module-level `FIXED_INBOX_DESTINATION: Destination = {type: 'inbox'}` constant (`DailyView.tsx`, `ReviewScreen.tsx`) — audited across the whole codebase, so nothing was left passing the now-removed optional shape.

**Weekly Review's Inbox-to-zero step gets a real Files pane.** Previously the only filing surface still using the old inline `ui/FileToPicker.tsx` list. Rebuilt as a two-pane layout — `ui/FileBrowserPane.tsx` (Projects/Areas/Resources tabs) on the left, the existing Tasks/Meetings content on the right — matching the Inbox tab's shape (§2.16/§2.18) exactly, via its own independently-named arm state (`inboxZeroArmTarget`, mirroring `InboxScreen.tsx`'s `armTarget` one-to-one, since these are two separate screens each owning their own local state, not a shared cross-screen one). This step's rows also gained Link (`onArmLink`) for the first time — the second explicit multiple-choice decision made during clarification, closing the asymmetry §2.18 had flagged as an unconfirmed assumption (see that section's updated writeup).

**One `ArmTarget` shape drives both File and Link.** Both `InboxScreen.tsx` and `ReviewScreen.tsx`'s Inbox-to-zero step now use an `ArmTarget = {type: 'task' | 'meeting'; index: number; intent: 'link' | 'file'}` — the same shape §2.18's `EditTarget` already had, with an `intent` discriminant added so one `armTarget`/`linkTarget` derivation can drive either arming flow through the identical `FileBrowserPane`. **Two roots while filing, three while linking**: whenever `intent === 'file'`, the Resources tab is structurally excluded from the `roots` array passed to `FileBrowserPane` — guaranteeing by construction that an Inbox item can never be filed into Resources, rather than relying on a runtime check that could be forgotten. `TaskRow.tsx`/`MeetingRow.tsx`'s row-level API collapsed to match: `onFile`/`fileCandidates` (which used to carry candidate data down to the row) became a single `onArmFile: () => void` mirroring the existing `onArmLink` exactly — the row just tells its parent to arm the parent's own Files pane; all Files-pane state stays owned by the parent screen, same as `onArmLink` already worked.

**Lasso capture loses its destination picker entirely.** `screens/CaptureScreen.tsx`'s destination is now always the source note's enclosing Project/Area (`findEnclosingItem`, unchanged) or Inbox if none — with **no override possible**, closing §2.9's original overridable-picker design. Removed: the `destination`/`destinationOpen` state, the destination-candidates computation block, the `DestinationRow` component, and every `domain/destination.ts` import this screen had (`destinationCandidates`, `sameDestination`) — the destination is now derived once (`loaded.defaultDestination`) and rendered as a static, non-interactive label. `domain/destination.ts` itself is untouched and stays live for unrelated reasons (`GoogleCalendarPanel.tsx`, `storage/dailyAggregate.ts`, `ItemsList.tsx` — see §2.11/§2.12's updated writeups).

**`ui/FileToPicker.tsx` and `ui/DestinationPicker.tsx` retired — asymmetrically.** Every live reference to `FileToPicker` is gone (confirmed by a full-codebase grep, not just the files this pass touched) — it is genuinely dead code now. `DestinationPicker.tsx` is **not** dead: `ui/GoogleCalendarPanel.tsx` (§2.17) still imports and renders it as its own copy-destination picker, an entirely separate consumer this feature never touched. Deleting `FileToPicker.tsx` (but not `DestinationPicker.tsx`) is manual cleanup still outstanding — see §4.

**An unrelated Lasso bug, found and fixed while implementing this feature.** Reported symptom: Lasso capture worked correctly the first time, then every subsequent capture showed the *previously recognized* text instead of the new selection's. Root cause in `App.tsx`: the Lasso button handler called `setMode('capture')` (a no-op when `mode` is already `'capture'` — React's `Object.is` bailout skips the re-render) and separately bumped a `captureNonceRef` **ref** (not state) to force `CaptureScreen`'s `key` to change and remount it fresh. Fixed by replacing `captureNonceRef` (`useRef`) with real state (`useState`) — `setCaptureNonce(n => n + 1)` now reliably forces the remount every time, first capture or not.

### 2.21 Refile (moving an already-filed item, and Inbox's File unified into it)

`ui/QuickAddWidget.tsx` (`docs/dev/technical-design-unified-quickadd.md`, steps 1-2 implemented 2026-09-08/09 but not yet its own design-overview.md section — this entry doesn't backfill that write-up, only the Refile piece) shipped with a reserved, inert "Refile" button in row 4's edit style, next to Delete. This pass wires it, and in doing so retires the row-level `onArmFile` "File" action §2.20 built: filing an Inbox item into a Project/Area and moving an already-filed item to a different one are the same operation, so there's now exactly one entry point for both — open the row for editing (already how every other per-item action works, Delete included), then tap Refile.

**Where it lives.** Refile is reachable on the three screens with a Files pane to arm — the Inbox tab, Weekly Review's Inbox-to-zero step, and (new) the Current tab (`ItemDetail.tsx`/`ProjectDataPanel.tsx`). Daily view and Review's add-only Week-ahead/stalled-project/neglected-area cards get no Refile control at all — `QuickAddWidget`'s new `onRefile?: () => void` prop is simply omitted there, the same optional-prop-absence convention `onArmLink`'s row-level read-only behavior already established (§2.18), so the button doesn't render rather than rendering disabled. Un-filing back to Inbox is explicitly out of scope — the destination picker only ever offers Projects/Areas, both Active-only, matching every other destination picker in the app (§2.19/§2.20).

**Mechanism: the same arm-a-Files-pane-tab-and-pick pattern, one level more general.** `storage/inboxFiling.ts`'s `fileInboxTask`/`fileInboxMeeting` (Inbox source only) had their target-side logic — resolve the target's cache entry, append, `saveTasks`/`saveMeetings`, write-through — extracted into shared `appendTaskToTarget`/`appendMeetingToTarget` functions, which both those and the Current tab's own refile now call. Inbox-tab/Review's-Inbox-to-zero-step's `armFileTarget`/`armInboxFileTarget` (§2.20's `ArmTarget.intent: 'file'`) are unchanged in shape but now armed from `QuickAddWidget`'s Refile button instead of a row-level "File" link. `ProjectDataPanel.tsx` gained the identical `ArmTarget` shape (`intent: 'link' | 'refile'`) it never needed before, since every item there is already filed — its own `handleRefilePick` guards against picking the item's own current location (a same-item "refile" would otherwise race two `saveTasks` writes against the same file from two stale in-memory snapshots) by silently cancelling arming rather than attempting the move.

**`ItemDetail.tsx` swaps its Files-pane roots while refile-arming.** Neither kind's normal roots offer a way to browse every Project (a Project's own roots have no `projects` sibling root) or, for an Area, every other Area — so `activeRoots` (mirroring §2.20's own root-restriction-by-construction preference) swaps to the same universal Projects(active)+Areas(active) pair the Inbox tab/Review use, whenever the bubbled-up `dataPanelLinkTarget` is an arming pick with `pickKind: 'folder'` — the same discriminator `LinkTarget`'s arming variant already carries for area-assignment's own folder pick (§2.19), reused here rather than adding a second signal.

**Requirements clarified in chat** before any code: whether Refile should replace Inbox's File action outright or stay a separate, filed-items-only action (chosen: replace it — one mechanism, not two); whether refiling should be able to send an item back to Inbox (chosen: no); and whether the destination list should be Active-only like every other picker or also allow On Hold (chosen: Active-only, for consistency). A fourth question — how Refile should work on screens with no Files pane to arm (Daily, Review's add-only steps) — was answered outside the structured options: skip Refile there entirely for now, revisit a picker for those screens later if it turns out to matter.

**Verified (initial pass)** via a brace/paren/bracket balance check across all eight touched files (no `node_modules`/real `tsc --noEmit`/`eslint` staged this session, same standing gap as every feature since §2.12) and a full re-stage-and-grep of every file immediately after committing to device, confirming byte-for-byte the write landed and no stray `onArmFile`/`fileActionText`/`refilePill` reference survived.

**Follow-up (2026-09-09, same day): a real bug found by using it, plus a UX rework requested in chat.** Tilman tried Refile and reported two things: (1) tapping Refile made the task's text and flow-state chip visibly vanish from the edit form, and (2) the Files pane's tab row changed shape the instant an arm started (Resources disappearing during refile-arming on Inbox/Review; the Current tab's whole root set swapping to an unrelated universal pair) — "very predictable behavior" and "don't add/remove tabs, just switch tabs and change behavior on tap" was the explicit ask, with a concrete "Browse tab" proposal.

*The vanishing-field bug.* Root cause: `armFileTarget`/`armInboxFileTarget`/`armRefileTarget` (and, latently, `armLinkTarget`/`armInboxLinkTarget` too - same shape, just not yet reported) all called `setEditTarget(null)`/`cancelEditTarget()` the moment an arm started - a leftover from when File was a row-level action independent of any open edit. Now that Refile only exists inside `QuickAddWidget`'s edit mode, clearing `editTarget` closed the very edit the tap came from, and the widget's own "editing → not editing" transition effect (`docs/dev/technical-design-unified-quickadd.md` §5's `wasEditingRef`) dutifully wiped its fields back to the (empty) create-mode draft - exactly the vanishing Tilman saw. Fixed across all three screens: arming a link or a refile no longer touches `editTarget` at all; instead, `cancelEditTarget` (already the one thing every "close this edit" path routes through - Cancel, or a successful Save/Delete) now also cancels any open arm, so an arm can never outlive the edit it was started from. Safe because `linkTarget`'s own derivation in all three screens already checks `armTarget` before ever falling through to `editTarget`'s unrelated "locate a linked file" branch.

*The Browse tab.* Requirements were re-clarified in chat (five focused questions, all answered directly - see §5's updated Refile entry) before touching code, given the added architectural surface. `ui/FileBrowserPane.tsx` gained two new `FileBrowserRoot` capabilities: `disabled` (a root's MiniTabs entry greys out and stops accepting taps without leaving `roots` - replacing the old pattern of filtering a root out of the array, or swapping the whole array, while arming), and a composite `sources`/`onNavigateToItem` pair for one new permanent "Browse" root that merges several physical directories (Projects + Areas) into its own always-Active-only, alphabetically-sorted top-level listing. Below that top level it's an entirely ordinary single-directory browse - only the merged depth-0 listing is special. Browse's own top-level tap behavior is three-way, all handled inside `FileBrowserPane` itself rather than by its callers: plain browsing (no arm active) calls the new `onNavigateToItem` callback instead of drilling in, which each screen wires to the same `App.tsx` `openItem` that Projects/Areas/Daily/Review already use to jump the "Current" tab to a Project/Area; refile-arming (`pickKind: 'folder'`) picks the tapped entry immediately, synthesizing the exact `(root, relativePath)` shape `storage/inboxFiling.ts`'s `resolveFilingPick` already expected (`'projects'`/`'areas'` plus a bare name) so no caller-side pick handler needed to change; link-arming (the default `pickKind: 'file'`) just falls through to the ordinary drill-in, letting a file inside a Project/Area be picked exactly like any other root.

Inbox tab and Review's Inbox-to-zero step: their old separate `projects`/`areas` roots are gone, replaced by one `browse` root alongside `resources` (which now renders `disabled` while refile-arming, rather than disappearing). The Current tab (`ItemDetail.tsx`) keeps its normal kind-specific roots (`Project Files`/`Resources`/`Areas`/`Area Files`, or `Area Files`/`Resources`/`Project Files`) exactly as they were, always visible, plus the new permanent `browse` root; while refile-arming, every root except Browse renders `disabled` (Browse is auto-switched-to via the pre-existing "arming with an explicit `root`" auto-navigate effect, since refiling always sets `root: 'browse'`) rather than the roots array being replaced. Area-assignment's own pre-existing `pickKind: 'folder'` arm (`ui/ItemStatusPanel.tsx`'s "Assign to Area…", `root: 'areas'`) is untouched and unaffected - `isRefileArming` discriminates the two by checking `root === 'browse'` specifically, not just `pickKind === 'folder'` alone.

### 2.22 Daily view: Focus/Projects/Areas panel

Two more new constants, `dailyCalendarMeetings`/`dailyCalendarGoogle`, replace `PAGE_SIZE.column`/`googleCalendarDaily` for Calendar's own two sub-tabs specifically (starting smaller, pending on-device tuning) — Calendar shrank its own row budget now that this panel sits underneath it in the same column; `PAGE_SIZE.column` itself is untouched, since Open tasks (the other column) is what gained the freed vertical space, not Calendar.

**Not yet verified on-device** (no `device_bash`/on-device build access this session, same standing caveat as every feature since §2.12) — a syntax-only check (no `node_modules`/RN types staged this session) is the extent of verification so far. Worth a dedicated on-device pass: the panel's fixed height actually matches across all three tabs at the tuned page size; arm-and-pick end to end for both kinds, including the "Focus is full" block still surfacing correctly if a race lets a stale candidate through; the mini-tab grey-out during an arm, and that switching to a different top-level tab mid-arm cancels silently with no error; the reduced Calendar row counts against the real device; and that the global alphabetical sort doesn't visibly regress any of `FileBrowserPane`'s other existing callers (Resources, Project Files, an Area's own Project Files, Browse).

### 2.23 Context tags

Fills the one open gap the Tags feature (§2.14) left: plain `#context` tags (e.g. `#mh`) get real UI. Tapping a tag already in a saved Task/Meeting's text sets a Daily-scoped "context" filter; while active, Daily becomes a hard filter to tag-matching items only, with the flow-state exclusion relaxed to let Next/due/Waiting-For/Someday through (Maybe still excluded even on a match). Requirements were clarified over two rounds of chat plus a Claude Design canvas (six artboards: Daily context off/active, Todo/Meeting edit tag-row pages) iterated over two more rounds, then written up as `docs/dev/technical-design-context-tags.md` before implementation, per this project's standing workflow.

**Tag extraction is app-wide; the filter view is Daily-only** — a deliberate scope split, called out because it's easy to under-scope by reading "Daily-only" too broadly. Every `QuickAddWidget` caller gets the tag-insert row; only `DailyView.tsx` gets the tappable filter.

**`domain/flowState.ts` gained `isContextTag(tag)`**, excluding `next`/`someday`/`maybe`/`now` and the `waiting-for`/`due:*` prefix families — the same reserved-tag set the flow-state chips already own, so a context tag can never collide with one. **`domain/markdown.ts`** gained `deriveMeetingFields(title)` (Meeting's counterpart to the `Task` side's existing `deriveTaskFields`) plus `extractContextTags`, `splitTextWithTags` (for rendering saved text as tappable segments), `insertTagAtPosition`, and `removeTagFromText`. `Meeting.tags` — present in `domain/types.ts` since the Tags feature but hardcoded to `[]` at every construction site until now — is finally populated everywhere a Meeting is created or edited, closing out the last of that hardcode.

**`storage/dailyAggregate.ts`'s `buildDailyAggregate` gained a 5th `contextTag` param.** When set, both the task and meeting loops (Daily and Inbox alike) become a hard filter to tag-matching items, the task loop still excluding `maybe`. The function stays a pure synchronous transform over the warm cache (§2.3) — no new I/O.

**New `storage/tagUsage.ts`** (AsyncStorage, mirrors `settingsStorage.ts`'s convention) tracks "last applied" recency, up to 30 tags, move-to-front on use — necessary bookkeeping since tags carry no timestamp in the files themselves. Recorded once per successful add/edit save from inside `QuickAddWidget`'s submit handlers, typed or tapped tags both count.

**New `ui/TagChips.tsx`** renders the recency-ranked, paginated tag row. Built as a **controlled** component (`page`/`onPageChange` owned by the caller) rather than internally-stateful, a deliberate departure from what the design doc's own implementation-detail note speculated — `QuickAddWidget`'s Row 3 needs to know the current page itself, to decide whether `FlowStateChips` still shares the line. **`ui/QuickAddWidget.tsx`'s Row 3** is a 3-way branch for Todo (page > 0 → wide `TagChips` alone; Waiting-For's existing mini-layout unchanged; otherwise → `FlowStateChips` + narrow `TagChips` sharing the line); Meeting's Row 3 has no flow chips to share space with, so it's always in the wide mode with the same `‹`/`›` paging.

**`ui/TaskRow.tsx`/`ui/MeetingRow.tsx`**: saved-text tags are now individually tappable via nested `<Text onPress>` segments (`splitTextWithTags`) — the same "spans inside a row's text become their own tap target" shape `ui/TaskBadges.tsx` already established for badges-after-text, just applied inline this time. The existing tap-row-to-edit gesture is unchanged. **`ui/TaskBadges.tsx`** gained a Someday visual cue (a small badge) for a Someday task surfaced only because it matched an active context — threaded through as `contextActive`, a boolean, not a new badge context, so every other caller is unaffected.

**`screens/DailyView.tsx`** owns the `dailyContext` state and its toggle, plus a small `#`/tag pill indicator (outline when inactive, filled with a `✕` when active) shown above the Calendar/Open-tasks columns. The filtered list itself is a `displayAggregate` recomputed with `contextTag` on every render — kept separate from the cached `aggregate` state specifically to avoid `load`'s stale-closure problem (`load` is a `useCallback` with an empty dependency array). `editingTaskEntry`/`editingMeetingEntry` deliberately keep reading the *unfiltered* `aggregate`, not `displayAggregate`, so toggling context mid-edit never yanks the row being edited out from under the user. ### 2.29 Observable cache, one shared add/mutate path, and the "where did it go" note (2026-09-20)

Bugfix + consolidation, written up as `docs/dev/technical-design-cache-subscription-and-shared-add-path.md` (with an "As built" section). **The bug:** in Week, a meeting filed to a Project/Area (tag in the title, "+ Add to <Name>", or the tag "New from this" appends) did not appear until something else re-rendered the screen; Inbox adds worked, Daily worked. **Cause:** the cache's write-through helpers mutate items in place, so a screen's `setItems(cache.items)` handed React the same array - a no-op state update. Inbox adds only worked because they also `setInbox(newObject)`; Daily only because its `refreshFromCache` also rebuilt an aggregate state object. (React skips an equal `setState` only once the fiber is idle - the first one after a real update still re-renders - which is why it looked intermittent; the regression test needs several adds in a row to reproduce it.)

**Observable cache.** `storage/dataCache.ts` keeps a version counter and `subscribeCache`/`getCacheVersion`; every mutation (rebuild, `ensureItemCached` push, every `updateItem*`, `removeCachedItem`, `clearCachedData`, abbreviation assignment/migration) calls `notifyCacheChanged()`. `ui/useCachedItems.ts` subscribes (plain `useState` tick + `useEffect`, no `useSyncExternalStore`) and returns a NEW array identity per change. Week, Daily, Review and Inbox use it in place of their `items` state; `refreshFromCache`/`refreshItemsFromCache` are gone from Week, Daily and Inbox. Daily's `aggregate` is now a per-render `const` derived from `items`/`inbox` (it used to be state). **Review's `aggregate` deliberately stays a frozen snapshot** (its steps must not drop rows mid-review) - only its `items` is live; its `refreshFromCache` still rebuilds that snapshot.

**One shared write path.** `storage/itemMutations.ts` (no React): `buildTask`/`buildMeeting` (one literal each - Capture's copies had drifted and lacked `linkedFile`), `addTaskToDestination`/`addMeetingToDestination`, `mutateEntryTasks`/`mutateEntryMeetings` (Daily/Week's Inbox-or-item resolve, stale-index check, save, write-through). Every function that may write the Inbox file takes an `InboxContext {inbox, basePath}` and RETURNS `{nextInbox}`; the screen does `if (nextInbox) setInbox(nextInbox)`. That return value replaces the old `inboxOverride` threading (Daily's `saveEntryTasks` wrapper still accepts it for the `#now` cohort clear). Adopted by Daily, Week, Review (add flow), Capture; Inbox and Project use the builders. **Side fix:** Review's Inbox-to-zero meeting add used to ignore its `destination`, so a meeting typed with a `#ABBR` tag ("+ Add to <Name>", tag stripped) was silently filed to the Inbox; it now files where the button says.

**"Where did it go" note.** `QuickAddWidget`'s optional `isMeetingDateVisible(date)` prop; when it returns false for a just-added meeting, Row 4's note becomes `✓ Added "<title, 16 chars…>" - tomorrow | next week | 09/28` (`domain/dateLabel.ts`'s `describeAddedDate`: today/tomorrow/yesterday, next/last ISO week, `MM/DD` in the current year, `YYYY-MM-DD` otherwise - always relative to the real today). Week passes "inside the displayed week"; Daily passes "the shown tab's own day" (the Google tab shows none, so the note always appears there); the focus-mode widget and every screen that lists all its meetings pass nothing and keep the plain message. No automatic navigation.

Verified off-device: tsc over all of `src/` (zero new errors; Capture's 8 pre-existing `linkedFile` errors are gone, 17 -> 9), the unused-symbol pass, `describeAddedDate` under four time zones, and Jest/react-test-renderer suites for the hook (including a test documenting the same-array no-op), the mutations module, the widget note, and real mounts of WeekView and DailyView (the WeekView repeated-add test fails against the pre-change screen and passes now). Not yet device-tested.

### 2.32 Project close-out and the archive PDF (2026-09-29)

Design: `docs/dev/technical-design-project-close-out.md`. It holds the requirements, the spike (`docs/dev/spike-project-archive-pdf.md`), the full design, the decisions (§11) and the as-built notes per slice (§12). UX mockups were approved before the design was written.

**What it does.** A Done Project goes through a 5-step wizard before it is archived:
1. **Checklist** (readiness)
2. **Contents** (what goes into the PDF)
3. **Outcomes** (which files move on to the Area or to Resources)
4. **PDF** (create it, open it in Supernote's reader, then tick "I checked")
5. **Archive** (the numbered list of operations, then "Archive now")

"Quick archive" runs only steps 1 and 5, with no PDF and no outcome moves. The result is the project folder at `Archive/<doneAt year>/[<Area>/]<Project>/`, plus one long-term PDF next to it, `<Project>.pdf`. The PDF has a cover, a linked table of contents, bookmarks, the project record (todos and meetings) and the included note pages. Files that aren't included are listed in an index with where they are.

**Entry points.**
- Review › "Done awaiting review" detail: "Close out…" and "Quick archive…", with a hint showing a close-out in progress (`planStatusLabel`).
- The Archive button on Projects in the other Review steps opens quick close-out.
- Item detail's status panel shows "🗄 Close out…" for Projects.
- `App.tsx` holds `closeOut {path, mode}` and renders `screens/CloseOutWizard.tsx` inside the Review tab instead of `ReviewScreen`. Leaving the wizard returns to Review.

**Readiness.** `domain/closeOut/readiness.ts` rates each finding by severity:
- Blockers: open todos, future meetings (Cancel / → Area / → Inbox; there are no meeting series), and a name collision at the archive target.
- Warnings: meetings not closed out, period (week/month) references, incoming links.
- Notices: unreadable notes, and whether the plugin was opened from a note inside the project.

The actions reuse `storage/itemMove.ts` (`moveTaskTo`, `moveMeetingTo`, `closeTask`, `cancelMeeting`). `ProjectDataPanel` still has its own refile code (§4).

**Plan and resume.** The wizard's state is a `## Close-out` section in `project.txt`, handled by `domain/closeOut/plan.ts` and `storage/closeOut/planStore.ts`. It holds the current step, the mode, only the deviations from the defaults (include/exclude, outcome moves), the PDF status and a journal of executed operations. It is a span-scoped section like every other one (§3). Leaving the wizard at any point and coming back resumes at the same step. Any change to contents or outcomes clears the PDF tick, so the checked PDF is always the one that gets archived.

**Lifecycle dates.** `domain/lifecycleDates.ts` keeps `doneAt` (stamped by `setItemStatus` on the first → Done, cleared on → Active) and `archivedAt` in the frontmatter's extra lines. The archive year comes from `doneAt`, and it can be edited in the checklist (`statusControl.setDoneDate`).

**Layering.**
- `domain/closeOut/`: `inventory.ts` (files → content groups, outcome candidates, time estimate), `readiness.ts`, `archiveDocument.ts` (project → `PdfDocument`), `archiveOps.ts` (the operation list shown in step 5 and executed), `archivePaths.ts`. All pure, tested with tsx.
- `storage/closeOut/`: `scan.ts` (folder walk plus page counts), `context.ts` (everything one wizard screen needs, `loadCloseOutContext`/`refreshCloseOutContext`), `pdf.ts`, and `execute.ts`. The executor is journaled and idempotent: outcome moves and link rewrites run first, then the PDF move, the folder move, and finally the `archivedAt` stamp at the new location. A failure stops without rollback, and running it again resumes.
- `ui/closeOut/` holds one component per step and `screens/CloseOutWizard.tsx` is the container.

**PDF pipeline (general-purpose, not close-out-specific).** The SDK has no PDF API, so the pipeline is built from three parts:
- `domain/pdf/` (`pdfDocument.ts`, `pdfLayout.ts`, `helveticaMetrics.ts`, `pdfSpec.ts`) turns an abstract document (headings, paragraphs, linked rows, images) into positioned pages. It uses anchors instead of page numbers and resolves them in several passes for the table of contents.
- `storage/pdfExport.ts` (`startPdfExport`) renders note pages with `PluginFileAPI.generateNotePng`, which already includes the template background. Temp PNGs go under `.gtdpara_tmp/<jobId>/` and are always cleaned up. It reports progress (render → layout → build) and can be cancelled.
- The native `PdfModule.kt` (`GtdParaPdf`) is a small PDF 1.4 writer: Flate grayscale images, Helvetica with WinAnsi encoding, link annotations and nested outlines. It writes a `.part` file and renames it when finished.

Any future "export X as PDF" feature should build a `PdfDocument` and call `startPdfExport`, nothing else. Existing PDFs are **not** merged into the archive PDF in v1; they are listed only (the spike crashed on a large-format page, and Tilman decided against pursuing it).

**Native additions.** `GtdParaFileModule` gains `moveFile`, `moveFolderMerge` (checks every collision before moving anything) and `deleteTempTree` (only paths inside `.gtdpara_tmp`).

**Shared UI built for this, reusable elsewhere:** `ui/PillButton`, `ui/ProgressBar`, `ui/StatusMarkRow`, `ui/wizard/StepIndicator` and `ui/wizard/WizardFrame` (header, step strip, back/next, e-ink refresh on step change). The steps also reuse `ReviewMasterDetail`, `PagedSection`, `FileBrowserPane` (browse mode with `onActiveLocationChange`, for "Move here") and `DateInput`.

**Status.** Slices 1–5 (native, PDF layout, export service, data model, new archive layout) have been device-tested by Tilman. Slices 6–10 (close-out domain, executor, wizard, wiring) are tsc-clean and pass Node/tsx tests (including an executor integration test with a forced failure and resume), but the full wizard has not been device-tested yet (tracked in the internal backlog).

- **Close-out and archive**: readiness finding `openMarks` (warning) with "Process ›"; archiving (close-out op `moveMarks` and direct `archiveItem`) moves the remaining lines into `Inbox.txt` first, re-pointed to the archived note, then clears the item's section.
- **Diagnostics**: integrity check `markNoteMissing`; debug bundle line `marks: open … · data … · pending icons …`.

## 3. Architectural guidelines for future changes

These are the rules this codebase has settled on. A change that doesn't fit one of these should probably explain why in its own comment, the same way the existing code explains its own deliberate deviations.

**Data architecture**

- Files are the single source of truth. Never add a second persisted store for Task/Meeting *content* — `AsyncStorage` is for plugin configuration only (§2.7), never PARA content.
- The cache (§2.3) must always be fully reproducible from a `rebuildCache`. If you add a field to `CachedItem`, it must be derivable purely from `loadProjectFile`'s own output — nothing should exist in the cache that isn't recoverable by re-reading the files.
- **Write-through is not optional.** Any new mutation of a Project/Area's tasks or meetings must call the file write (`saveTasks`/`saveMeetings`) *and then* the matching cache write (`updateItemTasks`/`updateItemMeetings`) in that order, in the same operation — write the file first, so a failed write never leaves the cache claiming a change that didn't actually persist.
- **Screens never poll or manually refresh the cache.** Read cached items with `useCachedItems()` (§2.29) and create/mutate Tasks and Meetings through `storage/itemMutations.ts` - never hand-write the Inbox-or-item branch or a Task/Meeting literal in a screen, and never `setItems(cache.items)` (the cache mutates in place, so that is a no-op). A new cache mutation helper must call `notifyCacheChanged()`.
- Reads should prefer the cache: use `ensureItemCached`/`findCachedItem`/`getCachedData` rather than calling `loadProjectFile` directly, unless there's a specific reason to force a live disk read (the way `ItemDetail`'s file-browser pane deliberately does, since it's a different kind of data — see §2.1).
- Any new content added to `project.txt`/`area.txt` beyond Tasks/Meetings must follow the same span-scoped `getSpan`/`setSpan` pattern in `markdown.ts` — never parse-and-regenerate the whole file. Regenerating the whole file is exactly the bug the original design's §6 open question was raised to prevent.
- `domain/` stays free of React Native and `sn-plugin-lib` imports, full stop. It's what keeps that code testable with plain `node` scripts (the pattern used throughout this project's history: a throwaway copy with `import type` for interfaces, run directly, no test framework needed). I/O and native calls belong in `storage/` or `supernote/`.
- Extending `Task`/`Meeting` needs a parser change, a serializer change, and a round-trip check — and must not corrupt a file written before the new field existed.
- Remember the extra-lines caveat from §2.2: content the parser doesn't recognize survives, but always moves to the end of its section on the next save. Don't design a feature that depends on preserved ordering between recognized and unrecognized lines.

- **File changes are visible and deletes are confirmed** (DEVELOPMENT-POLICY §3): moves, overwrites and deletes are announced before and after (`domain/fileChangeText.ts`); a delete needs a confirmation naming it, then FILE:DELETE, then `deleteEmptyFolder`. Temporary files only in the private temp folder.

**Styling**

- All font sizes come from `ui/theme.ts`'s `FONT` constant. No literal `fontSize` numbers in a `StyleSheet`. If a genuinely new size is needed, add it to `FONT` and justify it against the standing "max three sizes" rule rather than adding a fourth ad hoc.
- Navigation is `App.tsx`'s tab model (§2.1) — a new persistent screen is a new entry in `AppTab`/`TabBar`, not its own header/back-button. `TabBar` is the one place "✕ Close plugin" (`PluginManager.closePluginView()`) lives; a new tab doesn't repeat it. `CaptureScreen` is the one screen still allowed to be a bespoke full-screen overlay (`mode: 'capture'`), since it's deliberately not part of the tab shell.
- There's no centralized color theme yet (unlike `FONT`) — light/dark handling is ad hoc per screen via `useColorScheme()` plus local `textColor`/`borderColor`/`placeholderColor` variables, and `#2f6feb` is the de facto primary-action color. Copy the existing pattern from `Home.tsx`/`ItemDetail.tsx` for a new screen rather than inventing a different one; if this starts to feel repetitive, it's worth promoting to `ui/theme.ts` alongside `FONT`, but that hasn't been done.
- Any `ScrollView` holding a `TextInput` alongside other `Pressable`s needs `keyboardShouldPersistTaps="handled"`. RN's default swallows the first tap on a sibling `Pressable` as a text-field blur — this was the actual root cause of the original "+Add does nothing" bug, and it will recur in any new screen that omits this.
- Before fixing a fixed-width `TextInput`/chip/label, check it against the target device (§2.6's A5 X spec) and against the *longest* real value it needs to display in full without truncating or scrolling (e.g. a full `YYYY-MM-DD` date, not just today's) — a width picked purely by eyeballing the editor preview is a guess, and this project has already shipped one guess that was too narrow.
- Keep every `TextInput` - and anything the user needs to see or tap while one has focus (its own Save/Cancel, a validation error) - above roughly the bottom third of the screen (§2.6's on-screen-keyboard-panel note). Below that line is where the on-screen keyboard/handwriting panel appears and can cover it. This is why quick-add forms already sit above their list rather than below it; keep that placement when adding a new one rather than defaulting to "form below, list above."

**User-facing messages (§2.34)**

- Every error, warning, confirmation, pick state and success message goes through the central status slot (`useStatus`/`useErrorStatus`/`useStatusApi`) - don't render a new inline "⚠ …" line, and don't use `Alert.alert`. The only exception is a load error that replaces a pane's content (`LoadErrorNotice`).
- Mark the control concerned with `MarkWrap` (⚠ or ✓) when there is one; the text belongs in the slot.
- Give every publisher a stable id (`'<screen>.<purpose>'`); components that can be mounted twice need a per-instance suffix (`useErrorStatus` adds one).

**Navigation and lifecycle**

- `App.tsx`'s `reorient()` is the one place that decides what screen to land on when the plugin opens or is brought back to the foreground, and the one place that kicks off the background cache rebuild. New "what should happen when the plugin opens" behavior belongs there, not scattered across individual screens.
- A screen needing cross-project data on open (like Daily view) should read `getCachedData()` and fall back to `rebuildCache` only if nothing is cached — never run its own per-item filesystem scan. That was Daily view's original mistake, and it's exactly what made it slow before the cache layer existed.

**Reusable building blocks (§2.32)**

- Anything that produces a PDF builds a `domain/pdf` `PdfDocument` and goes through `storage/pdfExport.ts`. Don't write a second renderer or call the native writer directly.
- Multi-step flows use `ui/wizard/WizardFrame` + `StepIndicator`. Keep their state in a span-scoped section of the item's own file (as `## Close-out` does) so that they survive leaving the plugin.
- File moves that can fail halfway go through an operation list with a journal (`archiveOps.ts`/`execute.ts` pattern): shown to the user before running, idempotent, and resumable.
- Moving or closing Tasks/Meetings from outside their own screen goes through `storage/itemMove.ts`.
- **Address the Inbox through `paths.inboxFolder` of the cache's paths** (`getCachedData().paths`, or `resolveLivePaths(settings)` in storage code) - never `paths.base` and never `resolvePaths(settings)` alone, which don't know whether an old Inbox has moved yet (§2.38).

**Verification**

- Superseded 2026-10-01 by `docs/dev/DEVELOPMENT-POLICY.md` §7: pure logic gets Jest tests in `__tests__/` (`npm test`), scripts are checked with `npm run test:scripts`, and `npx tsc --noEmit` runs in the repository itself. Earlier code was verified with standalone Node scripts and a separate shim project; that is no longer the standard.

## 4. Outstanding scope

The working backlog (features, adjustments, bugs, technical debt) is kept outside this
repository, in the maintainers' internal list; bugs and ideas from users go to GitHub issues.
This section only lists open points that touch the architecture or the rules in §3, so a design
for a related change starts from them.

- **Moving items: one note step, several writes.** Since 0.6.0 every move goes through
  `moveEntryWithNote` (§2.40), but the append-then-remove write itself still lives at each call
  site (screen-local state in Inbox/Review/Current, the cache in Daily/Week/close-out). One shared
  write would remove that duplication; switching `ProjectDataPanel` changes how it refreshes.
- **Edit and arming state per screen.** The "one edit at a time" / Files-pane arming logic and
  the small error-wrapper around actions are re-implemented in Inbox, Current and Review (simpler
  copies in Daily and Week). A shared hook would be the place for future changes to it.
- **Refile without a Files pane.** Daily and Review's cards have no Refile, because there is no
  Files pane to arm (§2.21). It would need a picker overlay; only if it matters in practice.
- **Fixed-position screen layout** (idea, 2026-09-07). Key information in the same place per
  screen, for calmer reading and fewer e-ink redraws. Most screens are close already (fixed-height
  rows, paged lists); not designed further.
- **Working name.** `gtdpara` is used everywhere (`PluginConfig.json`, `app.json`, repository);
  whether it stays the final name is not decided.
